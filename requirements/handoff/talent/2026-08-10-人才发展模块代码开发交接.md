## 二、需求与设计依据

- [人才发展模块设计方案](../../人才发展模块设计方案.md)
- [人才发展模块第0轮基线与详细设计](../../人才发展模块第0轮基线与详细设计.md)

本轮实现遵循以下已经确认的边界：

1. 人才盘点是员工当前状态评价，职业能力模型是晋升标准，两者独立配置。
2. 晋升决策同时参考人才盘点、职业能力模型、KPI、业务考核和工作事故等证据。
3. 系统只形成部门建议和内部初步决策，不承接公司级审批流程。
4. 部门建议不等于最终结果；晋升、续签、调薪、奖励正式结果需独立登记并形成历史。
5. 业务考核只记录最终结果，不记录考试过程；本轮总分为 6 分。
6. KPI 页面实时查询人才发展侧的业务考核、工作事故扣分结果，不建立重复同步台账，也不覆盖主管评分或其他扣分项。

### 3.3 人才盘点

已实现：

- 多版本人才盘点模型，历史批次冻结模型版本。
- 评价维度、维度满分、评分档、等级区间和九宫格名称配置。
- 默认六维评价及 S/A/B/C/D 评分档。
- 一次添加多条维度、评分档和等级区间后统一保存。
- 发布前完整性校验，并以页面提示呈现业务错误。
- 半年盘点周期：上半年、下半年。
- 批次名称自动生成：`年份 + 上半年/下半年 + 人才盘点`。
- 创建批次时明确选择成员。
- 仅部门主管不纳入九宫格评价；组长及其他普通成员均可纳入。
- 同一员工在同一半年只能参加一个人才盘点批次。
- 逐员工评价、保存后反显、按钮状态控制、校准、确认结果和未确认批次删除。
- 九宫格计算：
  - 绩效 = 工作态度 + 能力度 + 产出度。
  - 潜力 = 忠诚度 + 匹配度 + 成长度。
- 九宫格横轴为潜力、纵轴为绩效，名称来自盘点模型配置。
- 最新盘点结果能够驱动人才总览九宫格人数统计。

默认九宫格名称为：

| 绩效 / 潜力 | 低 | 中 | 高 |
| --- | --- | --- | --- |
| 高 | 熟练员工 | 绩效之星 | 超级明星 |
| 中 | 基本胜任 | 中坚力量 | 潜力之星 |
| 低 | 问题员工 | 差距员工 | 待发展者 |

### 3.4 职业发展通道、岗位和员工档案

已实现：

- 职业通道限定为技术岗、管理岗。
- 岗位序列、人才岗位的多行配置和统一保存。
- 每一行可独立选择适用部门、职业通道、岗位序列并维护人才岗位。
- R1 至 R6 等职级段支持多行配置。
- 职级段可不设置细分档；需要时可配置如 R3-1、R3-2、R3-3。
- 员工档案维护入口已放到“人才履历”页签，并使用当前页签二级工作区。
- 员工档案可维护：
  - 入职日期。
  - 合同到期日期。
  - 人才岗位。
  - 职级及细分职级。
  - 入职薪资。
  - 当前薪资。
  - 档案备注。
- 岗位和职级选项读取规则配置，不再要求用户填写系统编码。
- 员工岗位只能选择其所属部门适用的岗位。
- 薪资字段受敏感信息权限保护。
- 正式晋升和调薪记录写入后可同步更新员工当前档案。

### 3.5 业务考核

已实现：

- 业务考核总分固定为当前确认的 6 分。
- 支持分数评分和等级评分。
- 支持首次考试、补考及最终不及格三种结果。
- 按考试科目平均分摊 6 分：
  - 首次及格：取得该科目满分。
  - 补考及格：取得该科目一半分数。
  - 最终不及格：0 分。
- 仅保存最终结果，不保存考试过程。
- 支持 XLSX/CSV 最终结果导入、预检、批次和错误行记录。
- 可确认批次并形成员工汇总结果。
- 向 KPI 提供的扣分提示为“实际所得分 - 6 分”。

### 3.6 工作事故

已实现：

- S/A/B/C/D 事故等级记录。
- 事故责任人、处罚动作、限制期、确认和作废。
- 当前 KPI 扣分规则：
  - D 级：每次扣 10 分。
  - C 级：每次扣 40 分。
  - 存在 S、A、B 任一级事故：工作事故项扣满 110 分。
- 同季度 C、D 事故累计扣分。
- 确认或作废事故后自动重算季度汇总。
- KPI 实时查询已确认事故产生的扣分结果。

### 3.7 KPI 联动

- 业务考核扣分提醒。

当前联动原则：

- 查询失败时不阻断 KPI 评分，页面给出不可用提示。
- 主管可结合提醒和其他扣分事项完成最终 KPI 评价。

1. 配置职业通道、岗位、职级和人才盘点模型。
2. 维护员工档案。
3. 创建半年盘点批次并完成所有成员评价。
4. 导入业务考核最终结果。
5. 录入工作事故。
6. 查看 KPI 详情中的实时扣分提醒。
7. 生成人才建议。
8. 登记公司正式结果。
9. 查询员工全部晋升、续签、调薪和奖励历史。

验收门槛：数据库结果、页面统计、权限范围和历史快照一致。

### 第 4 步：清理、拆分提交和发布准备

1. 清理未使用组件和 ESLint 警告。
2. 处理重复独立路由。
3. 将人才发展改动与产品管理等无关改动拆分。
4. 审阅 10 个迁移和数据兼容性。
5. 进行全量备份、迁移演练和回滚演练。
6. 再形成可评审的独立提交或 PR。

## 八、接手后的启动与检查命令

在仓库根目录执行：

```bash
npm run prisma:generate
npx prisma migrate status --config db/prisma.config.ts
npm run test:talent
./node_modules/.bin/tsc --noEmit
./node_modules/.bin/eslint 'src/app/(authenticated)/talent' src/server/talent 'src/app/(authenticated)/kpi/[id]/content.tsx' src/server/kpi/kpi-query.ts src/server/permissions/permission-constants.ts src/server/bootstrap/system-bootstrap.ts
npm run build
git diff --check
```

注意事项：

- Prisma 命令需使用 `--config db/prisma.config.ts`。
- 数据库结构变更后按“生成 Prisma Client → 应用迁移 → 重启服务”的顺序执行。
- 本项目没有通用 `npm test`，人才发展使用 `npm run test:talent`。
- 如果 Turbopack 在受限环境中出现端口或 IPC `EPERM`，应在允许绑定端口的环境重试，不能直接判定为代码失败。
- 开始修改前先保存当前 `git status`，保护工作区中不属于人才发展的用户改动。
