# 开发项目需求补录与完成前校验 — 产品/开发交接

**日期**：2026-10-27  
**仓库**：`C:\appdeploy\depot`（实现落代码库；本文档仅 handoff，不入库）  
**状态**：方案已定，待开发（V1）

---

## 1. 背景

- 不少**开发项目**在未登记需求时就被标为「已完成」，首版完成度无法统计。
- 系统现状：项目 **已完成 / 已关闭** 为终态，不能再挂需求（`findEditableProject`）；首版完成度只认需求侧开发工作量（`recalcProjectWorkloadSnapshot`：`needsDevelopment=true`、有工作量、非 `CLOSED`）。
- 日常「新增需求」仍仅面向**未终态**项目；需单独 **补录** 能力处理存量，并用 **完成前校验** 防止增量再犯。

---

## 2. 目标

| 目标 | 说明 |
|------|------|
| 存量 | 有权限用户可对**已终态的开发项目**补录需求，按需求**完成时间**重算首版完成度 |
| 增量 | **开发项目**变更为「已完成」前，必须先完成需求登记（至少一条有效需开发需求） |
| 管控 | 补录独立权限；操作可审计；与日常新增需求区分 |

---

## 3. 方案总览

| 线 | 作用 | 面向 |
|----|------|------|
| **A. 需求补录** | 解决存量 | 已是 **COMPLETED**（及待定 **CLOSED**）的**开发项目** |
| **B. 完成前校验** | 解决增量 | **开发项目**首次变为 **COMPLETED** 的所有入口 |

**非开发项目**：不提供补录入口、不参与「完成前必须有需求」规则（无首版完成度主统计路径）。

---

## 4. A. 需求补录

### 4.1 权限

- 新增独立权限（命名示例）：**「项目需求补录」** / `canBackfillProjectRequirement`（具体键名与权限矩阵对齐现有 `permission` 模块）。
- 默认授予范围由产品/组织定（如管理员、PMO、指定主管）；在角色矩阵可配。
- **无权限**：不展示「补录需求」按钮；服务端拒绝（403/业务错误）。

### 4.2 入口与可见性（含本次修正）

- **仅开发项目**（`needsDevelopment === true`）展示「补录需求」。
- **非开发项目**：**不提供补录入口**（UI 不渲染；服务端即使被调用也应拒绝）。
- 建议入口：项目列表/卡片/详情，与「新增需求」并列，文案 **「补录需求」**。
- **可补录的项目状态**：
  - **V1 必须**：`COMPLETED`
  - **CLOSED**：产品待定（建议 V1 **不允许**，或仅管理员 + 强审计）
- **不开放补录的状态**：`NOT_STARTED` / `IN_PROGRESS` / `LAUNCHED` → 仍用普通 **「新增需求」**。

### 4.3 补录表单（相对普通新增）

- **固定语义**：历史补录；操作日志、备注带 **「补录」** 标识。
- **项目**：只读（至少不可通过补录改项目状态）；仅创建需求并挂到当前项目。
- **字段与统计口径**（与现网 `recalcProjectWorkloadSnapshot` 一致）：
  - **是否需要开发**：补录场景固定为 **是**（与「仅开发项目可补录」一致，表单可隐藏或只读为「是」）。
  - **工作量（人天）**：必填（与「需开发且已完成」规则一致）。
  - **完成时间**：必填；用于首版/迭代划分——相对项目 **上线日 `launchedAt`**：完成日 ≤ 上线日 → 首版，否则 → 迭代；**未上线项目**按现网逻辑全部计入首版。
  - **需求状态**：默认 **已完成**，或允许 **已完成 / 延期完成**；禁止通过补录反复改动项目状态。
- **所属项目**：默认当前项目，不可改为其他项目（或仅展示不可选）。

### 4.4 保存与统计

- 保存后调用现有 **`recalcProjectWorkloadSnapshot(projectId)`**，更新 Project 表首版/迭代工作量及完成度展示口径。
- **价值跟踪已最终确认（`isFinal`）** — **V1 建议**：
  - **禁止补录**，提示：「项目已完成最终价值确认，不可补录需求；如需更正走管理员数据修正」。
  - 不在 V1 做「补录后同步改写冻结跟踪快照」。

### 4.5 服务端（概念）

- 专用 Server Action（推荐 `backfillQuarterlyWork` 或 `createQuarterlyWork` + `mode=backfill`）：
  - 校验：补录权限、`project.needsDevelopment === true`、项目状态 ∈ 允许集合、无 `isFinal`（V1）、字段校验。
  - **绕过** `findEditableProject` 对 COMPLETED/CLOSED 的「不可新增需求」限制，**不**改变项目 `status`。
  - 写 **操作日志**（项目 + 需求，备注含「补录」、操作人、时间）。

### 4.6 与现网 UI 的关系

- 已完成/已关闭项目的普通 **「新增需求」** 继续 **隐藏**（已实现）。
- **补录** 为独立按钮 + 独立权限，仅开发项目可见。

---

## 5. B. 开发项目 →「已完成」强制需求登记

### 5.1 规则

当 **`needsDevelopment === true`** 且项目要变为 **`COMPLETED`** 时（**所有入口**：编辑项目、状态变更、看板等）：

- 该项目下至少 **1 条** 计入统计的需求：
  - `needsDevelopment = true`
  - `deletedAt` 为空
  - `status !== CLOSED`
- **建议 V1 同步要求**：上述需求中至少一条已填 **工作量（人天）**，否则完成度仍为 null；拦截时列出缺工作量的需求名（与现网「改非开发项目」提示风格一致）。

**非开发项目**：不校验「完成前必须有需求」。

**CLOSED**：是否同样强制 — 产品可选（V1 可只做 COMPLETED）。

### 5.2 交互

- 拦截：明确文案，如「开发项目标记为已完成前，须登记至少一条需开发需求（含工作量）」。
- 可提供跳转：**新增需求**（若项目未终态）或 **补录需求**（若已终态且有补录权限）。

### 5.3 存量

- 不对历史已完成项目批量改状态；存量靠 **补录** 修数据；**完成前校验** 只防新数据。

## 7. 分期建议

## 8. 验收清单

1. **非开发项目**：任何状态均无「补录需求」；接口拒绝补录。
2. **开发项目 + 无补录权限**：无按钮；接口拒绝。
3. **开发项目 + 有权限 + COMPLETED**：可补录；保存后首版完成度随 **完成时间 / 上线日** 更新。
4. **开发项目 0 需求**：改「已完成」任意入口均拦截，文案清晰。
5. **进行中开发项目**：仅「新增需求」，不依赖补录权限。
6. **isFinal 项目**：禁止补录，提示明确。
7. 操作日志可检索「补录」。

## 9. 非目标（V1 不做）

- 非开发项目补录。
- 补录时修改项目状态或回退终态。
- 自动批量把历史无需求项目改回进行中。
- 无权限用户通过改 API 补录（必须服务端校验）。
