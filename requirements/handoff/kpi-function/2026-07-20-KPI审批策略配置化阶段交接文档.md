## 2. 今日已完成内容

### 2.1 审批策略主表 `KpiApprovalPolicy` 已落地

已在：

- `db/prisma/schema.prisma`
- `db/prisma/migrations/20260720000100_add_kpi_approval_policy/migration.sql`

新增主表：`KpiApprovalPolicy`

当前字段：

- `id`
- `scopeType`
- `departmentOrgNodeId`
- `name`
- `description`
- `isActive`
- `createdAt`
- `updatedAt`

当前约束：

- `@@unique([scopeType, departmentOrgNodeId, name])`
- `@@index([scopeType, departmentOrgNodeId, isActive])`

### 当前设计含义

这一版主表只承载“策略头信息”，还不承载步骤本身。

作用是先表达：

- 某个系统范围 / 某个部门范围
- 存在哪些审批策略
- 哪些策略处于启用状态

这里复用了当前代码库已存在的范围建模风格：

- `scopeType`
- `departmentOrgNodeId`
- 系统范围用 `departmentOrgNodeId = ""`

这和：

- `RoleMenuPermission`
- `RoleAnnualGoalPermission`

的风格保持一致，避免在审批策略里再创造一套新的范围语义。

---

### 2.2 审批策略步骤解析枚举已落地

已在：

- `db/prisma/schema.prisma`

新增枚举：`KpiApprovalResolverType`

当前支持：

- `TEAM_LEADER`
- `DEPARTMENT_MANAGER`
- `ADMIN`
- `EXPLICIT_USER`

### 当前设计含义

这一步不是为了立刻接运行逻辑，而是为了让下一张步骤表不再用裸字符串表达“这一步怎么找审批人”。

首版先覆盖当前最确定的解析类型：

- 从组织树里找组长
- 从部门范围找主管
- 找系统管理员
- 指定某个显式用户

这套枚举和 Phase 3 计划文件中对 `resolverType` 的设想是对齐的。

### 2.3 审批策略步骤表 `KpiApprovalPolicyStep` 已落地

已在：

- `db/prisma/schema.prisma`
- `db/prisma/migrations/20260720000200_add_kpi_approval_policy_step/migration.sql`

新增步骤表：`KpiApprovalPolicyStep`

当前字段：

- `id`
- `policyId`
- `stepOrder`
- `label`
- `ancestorDepth`
- `resolverType`
- `resolverUserId`
- `skipIfSelf`
- `skipIfDuplicateApprover`
- `allowSkipWhenNoApprover`
- `createdAt`
- `updatedAt`

当前约束与索引：

- `@@unique([policyId, stepOrder])`
- `@@index([policyId])`
- `@@index([resolverType])`
- `@@index([resolverUserId])`

### 当前设计含义

这张表已经具备表达“某套审批策略里的每一步”的最小结构。

当前已经能描述：

- 第几步审批
- 该步名称
- 该步如何找审批人
- 是否跳过本人
- 是否与前序审批人去重
- 找不到审批人是否允许跳过

还没做的，是让它真正参与：

- KPI 初始化
- 审批快照生成
- 审批流转判断

因此当前状态是：

> **数据结构已到位，运行时代码尚未接线。**
