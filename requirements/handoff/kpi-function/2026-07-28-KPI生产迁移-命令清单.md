## 核心原则（执行前必读）

1. **保留库升级**：不建新库替换，在原 SQLite 上操作。
2. **非 KPI 数据原样保留**：组织、用户、年度指标、非 KPI 权限等，迁移前后 SHA-256 摘要必须一致。
3. **KPI 数据允许清零**：权限、模板、审批策略、个人 KPI 全部清理后重新配置。
4. **禁止 `db push`**：生产禁止运行 `scripts/refresh-env-after-merge.sh` 和 `prisma db push`。
5. **共享权限表不能整表清空**：`OrgPermissionGrant` 只允许删除 `moduleKey = 'KPI'` 的行。

---

## 数据边界速查

### 必须原样保留

- 组织与用户：`User`、`OrgNode`、`OrgClosure`
- 非 KPI 权限：`MenuPermission`、`RoleMenuPermission`、`AnnualGoalPermission`、`RoleAnnualGoalPermission`、`OrgPermissionGrant`（`moduleKey <> 'KPI'`）
- 年度指标：`AnnualGoalPlan`、`AnnualGoalMetric`、`AnnualGoalMetricSource`、`AnnualGoalQuarterTarget`、`AnnualGoalProgress`、`AnnualGoalRevisionLog`
- 其他业务：`Project`、`QuarterlyWork`、`Notification`、`TodoItem` 等

### 允许清理并重配

| 类别 | 表（清理顺序：子表 → 父表） |
| --- | --- |
| KPI 权限 | `OrgPermissionGrant`（仅 `moduleKey = 'KPI'`） |
| 个人 KPI | `PersonalKpiItemStepScore` → `PersonalKpiActionLog` → `PersonalKpiApprovalStep` → `PersonalKpiItem` → `PersonalKpi` |
| 审批策略 | `KpiApprovalPolicyStep` → `KpiApprovalPolicy` |
| KPI 模板 | `KpiTemplateAssignment` → `KpiTemplateItem` → `KpiTemplate` |

## 生产库状态分型（预检决定路径）

预检会在 `01-preflight.ps1` 中自动执行，也可本地只读验证：

```bash
npm run kpi:migration:preflight -- \
  --database /absolute/path/prod.db \
  --output /absolute/path/preflight.json
```

| 状态 | 特征 | 处理 |
| --- | --- | --- |
| **A** 标准旧库 | migration 连续，KPI 新结构未建立 | 备份 → 保全迁移 → `migrate deploy` |
| **B** 已 db push | 新结构已有，6 条 KPI migration 未登记 | 定向清理 KPI 数据 → 验证结构 → 对齐 history |
| **C** 混合状态 | 部分表/字段存在 | 幂等修复 → 逐条对齐 history |
| **D** 异常库 | 完整性失败 / failed migration / 保留数据异常 | **停止发布**，专项修复 |

**2026-07-28 演练库实测为 B 型**（`B_DB_PUSHED`，缺失 KPI migration 6 条，integrity ok）。

## 阶段 B：预检（T-3～7 天，生产机不停服）

以管理员或部署账号打开 **PowerShell**，进入项目目录：

```powershell
cd C:\appdeploy\depot
Set-ExecutionPolicy -Scope Process Bypass

# 拉最新代码
git pull
npm install --registry=https://registry.npmmirror.com

# 0. 环境检查（只读）
.\scripts\kpi-production\00-check-environment.ps1
```

若 PM2 进程无法唯一识别：

```powershell
pm2 list
$env:KPI_PM2_SERVICE_NAME = "pm2 list 中的实际进程名"
.\scripts\kpi-production\00-check-environment.ps1
```

选定本次运行编号（**01～07 全部共用，不可重复**）：

```powershell
$RunId = "20260728-kpi-policy-v1"
```

只读预检（**不修改生产数据**）：

```powershell
.\scripts\kpi-production\01-preflight.ps1 -RunId $RunId
```

预检输出目录：

```text

```

确认预检结论为 A/B/C 且非 D 后再安排维护窗口。

## 阶段 C：正式迁移（维护窗口，停服）

> **规则**：任一步出现红色错误，立即停止，不执行下一步。  
> **规则**：06 必须显示 `PASS` 才能执行 07。  
> **规则**：04 会在修改数据前自动生成完整备份。

```powershell
cd C:\appdeploy\depot
Set-ExecutionPolicy -Scope Process Bypass
$RunId = "20260728-kpi-policy-v1"   # 与预检阶段相同

# 1. 只读预检（维护窗口内可再跑一遍确认）
.\scripts\kpi-production\01-preflight.ps1 -RunId $RunId

# 2. 停止 PM2，确认 SQLite 文件已释放
.\scripts\kpi-production\02-stop-service.ps1 -RunId $RunId

# 3. 备份旧 .next、生成 Prisma Client、构建新版
.\scripts\kpi-production\03-build-release.ps1 -RunId $RunId

# 4. 备份数据库 + 定向清理 KPI 数据（事务内执行）
.\scripts\kpi-production\04-migrate-data.ps1 -RunId $RunId

# 5. 对齐 6 条 KPI migration history + migrate deploy
.\scripts\kpi-production\05-align-and-deploy.ps1 -RunId $RunId

# 6. 校验保留数据、KPI 清理结果、migration 状态（必须 PASS）
.\scripts\kpi-production\06-verify.ps1 -RunId $RunId

# 7. 启动服务 + HTTP 冒烟
.\scripts\kpi-production\07-start-and-smoke.ps1 -RunId $RunId
```

### 步骤对照表

| 步骤 | 脚本 | 作用 | 是否改库 |
| --- | --- | --- | --- |
| 00 | `00-check-environment.ps1` | 路径、Node、NPM、PM2 | 否 |
| 01 | `01-preflight.ps1` | 只读预检 + dry-run | 否 |
| 02 | `02-stop-service.ps1` | 停 PM2 + WAL checkpoint | 否 |
| 03 | `03-build-release.ps1` | 构建新版 | 否 |
| 04 | `04-migrate-data.ps1` | 备份 + KPI 定向清理 | **是** |
| 05 | `05-align-and-deploy.ps1` | 对齐 history + deploy | **是** |
| 06 | `06-verify.ps1` | 保留数据 / 清理 / migration 验证 | 否 |
| 07 | `07-start-and-smoke.ps1` | 启动 + 冒烟 | 否 |

### 07 冒烟预期

| 检查 | 预期 |
| --- | --- |
| `/login` | HTTP 200 |
| `/kpi` 未登录 | HTTP 302 或 307 → `/login` |
| `/organization` 未登录 | HTTP 302 或 307 → `/login` |

## 阶段 D：迁移后业务配置（脚本不代做）

结构迁移成功后，**按顺序**人工恢复 KPI 业务：

1. 配置 KPI 角色权限和指定用户权限
2. 创建并启用**系统默认审批策略**（全局唯一启用）
3. 按需创建部门覆盖策略（每部门最多一个启用策略）
4. 导入或创建 KPI 模板 + 设置适用范围
5. 验证策略能解析出审批人
6. **以上完成后**再初始化目标季度 KPI
7. 抽查成员 / 组长 / 主管 / 管理员权限

## 回滚

**触发条件（任一即回滚）：**

- 组织 / 用户 / 年度指标 / 非 KPI 权限摘要有变化
- 数据库完整性失败或 migration failed
- 新版应用无法启动
- KPI 重配 / 初始化无法完成

先查看回滚目标（不修改文件）：

```powershell
$RunId = "20260728-kpi-policy-v1"
.\scripts\kpi-production\08-rollback.ps1 -RunId $RunId
```

确认后执行：

```powershell
.\scripts\kpi-production\08-rollback.ps1 `
  -RunId $RunId `
  -Execute `
  -Confirm ROLLBACK_KPI_PRODUCTION
```

回滚会：停服务 → 验证备份 → 保存失败现场 → 恢复升级前数据库 → 恢复旧 `.next` → 重启服务。

若发布系统另有版本回滚命令：

```powershell
$env:KPI_ROLLBACK_CODE_COMMAND = "生产发布系统的回滚命令"
```

## 底层工具命令（高级 / 排障）

生产编排脚本内部调用以下 npm 命令，一般无需手工执行：

```bash
# 只读预检
npm run kpi:migration:preflight -- --database <path> --output <json>

# KPI 定向清理（默认 dry-run）
npm run kpi:migration:run -- --database <path>
npm run kpi:migration:run -- --database <path> --backup <path> --baseline-out <path> --result-out <path> --execute --confirm RESET_KPI_DATA

# migration history 对齐
npm run kpi:migration:align -- --database <path> --baseline <path>
npm run kpi:migration:align -- --database <path> --baseline <path> --execute --confirm ALIGN_KPI_MIGRATION_HISTORY

# 迁移后验证
npm run kpi:migration:verify -- --database <path> --baseline <path> --output <json>
```
