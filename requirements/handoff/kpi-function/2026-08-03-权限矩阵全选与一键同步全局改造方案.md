# 权限矩阵全选与一键同步全局改造方案

## 1. 文档信息

- 编制日期：2026-08-03
- 开发工作区：`depot-coordination/depot-KPI`
- 目标页面：组织与权限 → 权限
- 改造范围：菜单权限、年度指标权限、KPI 权限
- 当前阶段：方案与执行计划，暂不修改功能代码
- 不在本次范围：KPI 审批策略、成员显式授权、组织架构管理

## 2. 改造背景

当前三类角色权限均使用“能力项 × 角色”的权限矩阵：

- 菜单权限
- 年度指标权限
- KPI 权限

现有界面支持单个单元格开关、保存当前范围，以及在系统范围内把单个权限单元格同步到全部部门。随着能力项和角色增加，存在两个明显效率问题：

1. 同一角色需要开通多项权限时，只能逐个点击单元格。
2. 系统权限需要覆盖到全部部门时，只能逐个单元格执行“应用到全部部门”。

本次拟增加：

1. 权限矩阵批量全选/清空。
2. 当前权限模块支持“保存并同步本次变更”和“完整同步至所有部门”。

## 3. 现有实现评估

### 3.1 前端状态

三类权限已经分别维护完整的草稿矩阵：

- `draftRoleMenuCells`
- `draftAnnualGoalCells`
- `draftKpiCells`

每个单元格均包含：

```text
allowed
source
explicit
inherited
```

因此“全选”不需要修改数据库结构，只需要按当前权限范围批量更新草稿状态。

### 3.2 当前保存能力

已有三个完整矩阵保存入口：

- `saveRoleMenuPermissions`
- `saveAnnualGoalRolePermissions`
- `saveKpiRolePermissions`

当前保存只作用于系统范围或当前部门范围，不会自动覆盖其他部门。

### 3.3 当前同步能力

已有三个单单元格同步入口：

- `applyRoleMenuPermissionToAllDepartments`
- `applyAnnualGoalPermissionToAllDepartments`
- `applyKpiPermissionToAllDepartments`

它们一次只接受一个 `permissionId + roleType + allowed`，因此用户必须逐格同步。

### 3.4 数据库影响

本次只扩展批量操作逻辑，不新增表、不新增字段，原则上不需要 Prisma migration。

## 4. 已确定的产品方案

## 4.1 “全选”的作用范围

在三类权限矩阵中统一提供两级批量选择：

1. 全矩阵全选/清空：作用于当前页全部可编辑单元格。
2. 按角色列全选/清空：作用于某个角色下全部可编辑能力项。

第一版不增加“按能力项行全选”，避免每一行增加额外控件导致矩阵变得拥挤。如后续确有高频需求，再单独增加。

### 全矩阵控制

在矩阵左上角“菜单”或“能力项”标题旁增加三态复选框：

- 全部可编辑单元格开启：选中。
- 全部可编辑单元格关闭：未选中。
- 部分开启：半选状态。

点击规则：

- 当前不是全部开启时，点击后全选。
- 当前已经全部开启时，点击后全部清空。

### 角色列控制

每个角色列标题增加三态复选框，例如：

```text
☑ 初始管理员
◩ 部门主管
□ 组长
□ 普通成员
```

点击后只批量调整该角色列。

### 草稿与保存

全选/清空只修改前端草稿，不立即写数据库：

1. 操作后显示“有未保存的权限调整”。
2. 用户可以点击“取消”恢复保存前状态。
3. 点击“保存”后才写入当前范围。

这与现有单格操作行为保持一致。

## 4.2 不可修改权限处理

菜单权限中，管理员的以下核心入口继续保持强制开启：

- `/organization`
- `/dashboard`

批量全选或清空时必须跳过这些锁定单元格，不能因为“全部清空”而关闭核心入口。

所有批量操作均只能修改当前用户有权编辑的单元格；无权限编辑的矩阵只显示状态，不显示批量控件。

## 4.3 部门继承权限处理

部门范围内存在系统继承值。对部门矩阵执行全选/清空后：

- 被批量修改的单元格转为部门显式配置。
- `source` 更新为 `DEPARTMENT`。
- `explicit` 更新为 `true`。
- `inherited` 更新为 `false`。

点击“取消”恢复原继承状态。

本次不增加“整列恢复继承”功能；如后续需要，可增加独立的“恢复系统默认”操作，避免把“清空”与“恢复继承”混为一谈。

## 4.4 两种全局同步的定义

系统范围提供两个独立操作：

1. **保存并同步本次变更**：保存系统矩阵，只把与当前已保存系统值相比发生变化的权限单元格覆盖到所有现有部门；其余单元格保留部门现有配置。
2. **完整同步至所有部门**：保存系统矩阵，并用当前模块完整角色权限矩阵覆盖所有现有部门。

例如，在“KPI 权限”页执行该操作，只同步 KPI 权限，不同时修改菜单权限和年度指标权限。

采用“当前模块整体同步”，不设计一个同时覆盖三大权限模块的总按钮，原因是：

1. 降低误操作影响范围。
2. 确认弹窗可以清楚展示本次修改的模块。
3. 三类权限底层表结构和保存规则不同，分模块事务更容易验证和回滚。

## 4.5 一键同步按钮

仅满足以下条件时显示：

- 当前用户为系统管理员。
- 当前范围为“全部/系统”。
- 当前页面为菜单权限、年度指标权限或 KPI 权限。

按钮名称：

```text
保存并同步本次变更
完整同步至所有部门
```

按钮直接使用当前草稿矩阵，允许用户完成全选后一次提交，无需先单独点击“保存”。

仍保留现有“保存”按钮：

- 保存：只更新当前系统范围。
- 保存并同步本次变更：仅传播本次权限值变化。
- 完整同步至所有部门：用完整矩阵覆盖全部现有部门。

## 4.6 同步确认弹窗

两个同步操作均为高风险操作，提交前都必须二次确认。弹窗展示：

- 权限模块名称。
- 将覆盖的部门数量。
- 将同步的角色数量和能力项数量。
- 当前草稿相比已保存系统权限的变更数量。
- 明确提示部门现有显式配置会被覆盖。

示例：

```text
将保存当前 KPI 权限，并覆盖同步至 2 个部门。
同步范围：4 个角色 × 10 个能力项。
当前有 18 个单元格发生变化。
同步后，各部门现有 KPI 角色权限配置将被替换。
```

确认按钮使用明确文案：

```text
确认同步本次变更
确认完整覆盖所有部门
```

## 4.7 新增部门的处理

本次“一键同步”只覆盖执行时已经存在的部门。

后续新增部门仍按现有系统权限继承规则工作，不自动复制过去某次同步产生的部门显式配置。本次不新增“自动持续同步”机制。

## 4.8 现有单格同步入口

建议在整体同步功能验收稳定后，移除单元格悬浮的魔法棒同步按钮，原因是：

- 用户主要需求已经由整体同步覆盖。
- 同时保留两种同步方式容易混淆“同步一个单元格”和“同步整个模块”。
- 移除后矩阵更简洁，移动端和窄屏下也更容易操作。

实施时可以分两步：第一轮先保留作为兼容入口；整体同步验证通过后再决定是否删除。

## 5. 交互布局建议

三类权限页面统一为：

```text
权限标题                       [取消] [保存] [保存并同步至所有部门]
有未保存的权限调整

[全选] 能力项     [全选] 初始管理员  [全选] 部门主管  [全选] 组长  [全选] 普通成员
权限项 1               □                □             □          □
权限项 2               □                □             □          □
```

部门范围页面只显示：

```text
[取消] [保存]
```

不会显示“保存并同步至所有部门”。

## 6. 技术方案

## 6.1 前端通用批量更新函数

为三套草稿状态抽取统一的纯函数，输入：

```text
当前矩阵
目标单元格键集合
目标 allowed 值
当前 scopeType
锁定单元格集合
```

输出新的矩阵状态。所有被修改的单元格统一写入：

```text
allowed: true/false
source: 当前 scopeType
explicit: true
inherited: false
```

建议增加辅助函数：

- `getPermissionSelectionState`：计算选中、未选中、半选。
- `setPermissionCellsAllowed`：批量修改目标单元格。
- `countPermissionCellChanges`：计算全部草稿状态变化。
- `countPermissionValueChanges`：只计算 `allowed` 值变化，决定“同步本次变更”的实际范围。

这些函数应放在可单元测试的独立模块中，避免三套页面复制逻辑。

## 6.2 后端批量同步入口

新增六个 Server Action，分别对应差量与完整同步：

- `saveAndApplyRoleMenuPermissionChangesToAllDepartments`
- `saveAndApplyAnnualGoalPermissionChangesToAllDepartments`
- `saveAndApplyKpiPermissionChangesToAllDepartments`

- `saveAndApplyRoleMenuPermissionsToAllDepartments`
- `saveAndApplyAnnualGoalPermissionsToAllDepartments`
- `saveAndApplyKpiPermissionsToAllDepartments`

它们统一接收：

```text
scopeType=SYSTEM
departmentOrgNodeId=""
permissions=<完整矩阵 JSON>
```

服务端必须重新校验：

- 当前用户是系统管理员。
- scope 必须是系统范围。
- 角色值合法。
- 权限 ID/能力 Key 合法。
- 请求包含完整目标矩阵，不能只相信客户端显示状态。
- 菜单管理员核心入口强制开启。

## 6.3 事务规则

每个权限模块的一次同步必须在同一个数据库事务内完成。服务端先比较数据库中当前系统矩阵与提交矩阵，不能信任客户端传入的变更范围。

差量同步：

1. 规范化完整矩阵并计算真正发生变化的角色/权限单元格。
2. 保存系统矩阵。
3. 只删除并重建所有部门的变化单元格。
4. 保留其他部门独立配置。

完整同步：

1. 校验并规范化完整矩阵。
2. 更新系统范围权限。
3. 查询全部现有部门。
4. 删除这些部门在当前模块下的旧显式角色权限。
5. 根据系统矩阵批量创建部门显式权限。
6. 任一步骤失败时整体回滚。

不能先保存系统权限、再逐部门调用旧单格同步 Action，否则中途失败会造成部门之间状态不一致。

## 6.4 三类权限的持久化差异

### 菜单权限

- 表：`RoleMenuPermission`
- 同步 `allowed=true/false` 的完整显式矩阵。
- 管理员核心入口强制为 `true`。

### 年度指标权限

- 表：`RoleAnnualGoalPermission`
- 同步 `allowed=true/false` 的完整显式矩阵。
- 同步前继续执行权限定义 upsert，避免定义缺失。

### KPI 权限

- 表：`OrgPermissionGrant`
- 只为 `allowed=true` 的单元格创建授权记录。
- 系统记录 `orgNodeId=null`，部门记录使用对应部门节点 ID。
- `scopeType` 继续按角色映射为 `ALL/SUBTREE/NODE/SELF`。
- 只处理 `subjectType=ROLE`，不得影响成员显式授权。

## 6.5 并发与重复提交

- Server Action 使用事务保证原子性。
- 提交期间禁用“保存”“同步”和矩阵编辑控件。
- 重复提交相同完整矩阵应得到相同结果，不能产生重复授权。
- 成功后刷新组织权限页，以数据库结果重新初始化草稿。

## 6.6 数据库迁移

不需要新增数据库 migration。

如开发过程中发现现有唯一索引不能防止重复授权，应先单独评估，不在本方案中顺带修改生产数据结构。

## 7. 权限与安全边界

1. 系统管理员可以在系统范围执行“保存并同步至所有部门”。
2. 部门主管可以在有权管理的部门内使用全选/清空和保存。
3. 部门主管不能看到或调用全局同步入口。
4. 即使绕过前端提交，服务端也必须拒绝非管理员全局同步。
5. 全局同步只修改目标模块的角色权限。
6. KPI 全局同步不得删除 `subjectType=USER` 的成员显式授权。
7. 菜单核心入口不得被全选清空或批量同步关闭。

## 8. 自动化测试方案

## 8.1 前端纯函数测试

- 全矩阵从部分选中变为全选。
- 全矩阵已经全选时切换为清空。
- 单角色列全选。
- 单角色列清空。
- 半选状态计算正确。
- 锁定单元格不参与清空。
- 部门继承单元格批量修改后变为显式配置。
- 取消后恢复初始矩阵。
- 变更数量计算正确。

## 8.2 Server Action/服务层测试

三类权限分别验证：

- 系统矩阵保存成功。
- 所有现有部门得到一致的完整矩阵。
- 部门原显式配置被覆盖。
- 任一步骤失败时系统和部门同时回滚。
- 非管理员调用被拒绝。
- 部门范围调用被拒绝。
- 无效角色或权限 ID 被拒绝。
- 重复同步结果幂等。

专项验证：

- 菜单核心入口始终保留。
- KPI 成员显式授权保持不变。
- KPI 关闭权限时对应角色授权被删除。
- 年度指标权限定义缺失时能够安全补齐。

## 8.3 页面验收

菜单权限、年度指标权限、KPI 权限逐页检查：

- 全矩阵全选/清空。
- 每个角色列全选/清空。
- 半选状态显示。
- 取消恢复。
- 普通保存只影响当前范围。
- 保存并同步覆盖全部现有部门。
- 确认弹窗中的部门数、角色数、权限数和变更数正确。
- 部门主管看不到全局同步入口。

## 10. 验收标准

满足以下条件后视为改造完成：

1. 三类权限矩阵均支持全矩阵全选/清空。
2. 三类权限矩阵均支持按角色列全选/清空。
3. 批量选择保留现有草稿、取消和保存语义。
4. 菜单管理员核心入口不会被批量关闭。
5. 系统管理员可以选择只同步本次变更，或把当前模块完整矩阵同步至全部现有部门。
6. 部门主管不能执行全局同步。
7. 同步操作在单事务中完成，失败时全部回滚。
8. KPI 成员显式授权不受全局同步影响。
9. 新增部门继续使用现有继承逻辑。
10. 自动化测试、数据库测试和生产构建全部通过。

## 11. 风险与控制

### 11.1 误操作覆盖部门配置

控制措施：仅管理员可执行；强制确认；显示影响部门数和变更数；按模块同步，不提供跨三模块总同步。

### 11.2 未保存草稿与同步值不一致

控制措施：两个同步按钮都直接提交当前完整草稿，并在同一事务中保存系统值和部门值；差量范围由服务端依据数据库已保存值计算。

### 11.3 KPI 显式用户授权被误删

控制措施：删除和重建条件必须固定为 `moduleKey=KPI + subjectType=ROLE`，增加保护性集成测试。

### 11.4 菜单核心入口被关闭

控制措施：前端跳过锁定单元格，服务端再次强制管理员的 `/organization` 和 `/dashboard` 为开启。

### 11.5 大量部门导致写入放大

控制措施：每个模块使用批量删除和 `createMany`，禁止逐部门、逐单元格调用 Server Action；事务内只查询一次部门列表。

## 12. 开始实施前的确认项

建议实施前确认以下产品细节：

1. 是否接受“全选”同时包含全矩阵和按角色列两种能力。
2. 是否确认全局同步以“当前权限模块”为单位，而不是一次同步菜单、年度指标和 KPI 三个模块。
3. 是否确认同步按钮直接使用未保存草稿，并命名为“保存并同步至所有部门”。
4. 整体同步上线后，是否移除当前单元格悬浮的同步按钮。
