# KPI 列表得分展示改造 — 开发环境交接

**日期**：2026-09-17  
**范围**：仅在**开发环境**改造与验证；**不在现网**直接改代码、不执行现网 `depot-prod.sh pull/build`。  
**代码仓库**：`C:\appdeploy\depot`  
**关联页面**：`/kpi`（KPI 管理列表）

---

## 1. 背景与问题

现网 KPI 列表仅一列「得分」，取值逻辑为：

```text
finalScore ?? managerScore ?? leaderScore ?? selfScore ?? 0
```

（实现位置：`src/server/kpi/kpi-query.ts` 列表行组装。）

同时，任意阶段保存/提交评分时，`src/server/kpi/actions.ts` 会**一次性回写** `PersonalKpi` 的 `selfScore`、`leaderScore`、`managerScore`、`finalScore`。未填扣分的后续阶段按「指标满分（通常 110）− 0 扣分」计算，**未完成的阶段也会被写成 110**。

结果：同事只完成自评且自评低于 110 时，列表仍常显示 **110**（尤其进入组长评/主管评后，兜底链优先展示已被占位写满的 `leaderScore`/`managerScore`）。

详情页（`/kpi/[id]`）已是指标级「自评 / 组长评 / 主管评」+ 汇总行「考勤分 / 最终绩效总分」，**列表与详情口径不一致**。

---

## 2. 改造目标

将列表原单列「得分」改为 **4 列**（表头文案固定如下）：

| 列名 | 含义 |
|------|------|
| **自评** | 自评阶段汇总分（指标满分合计 − 自评扣分合计） |
| **组长评** | 组长评阶段汇总分 |
| **主管评** | 主管评阶段汇总分 |
| **最终绩效总分** | 主管评汇总 + 考勤分（与详情页「最终绩效总分」一致） |

**未完成阶段**：对应单元格显示 **「—」**，不展示占位 110 或兜底链结果。

**保持不变**：

- 「KPI 等级」列仍用终审完成后的 `finalRatingName`（及现有等级逻辑）。
- 顶部阶段统计（初始化 / 自评 / 组长评 / …）不改语义。
- 详情页交互与字段含义为列表的权威参考，列表只做对齐展示。

---

## 3. 展示规则（何时有数、何时为「—」）

复用列表行已有 **`completedProgressStages`**（与 `buildKpiCompletedProgressStages` 一致，见 `src/server/kpi/approval-workflow.ts`）。

| 列 | 阶段完成条件 | 取值字段 | 未完成显示 |
|----|--------------|----------|------------|
| 自评 | `completedProgressStages.selfReview === true` | `PersonalKpi.selfScore` | — |
| 组长评 | `completedProgressStages.leader === true` | `PersonalKpi.leaderScore` | — |
| 主管评 | `completedProgressStages.manager === true` | `PersonalKpi.managerScore` | — |
| 最终绩效总分 | `completedProgressStages.final === true`（终审完成） | `PersonalKpi.finalScore` | — |

说明：

- **自评**：以「已离开自评期」为准（`!isSelfReviewStatus(status)`），与现有 `selfReview` 完成标记一致；**自评草稿保存未提交**建议仍显示「—」（与产品此前「提交后才展示」一致）。
- **最终绩效总分**：仅在 **终审阶段完成** 后展示；进行中仅主管评完成、终审未做时，前三列可能有数，本列为「—」。
- 阶段已完成但 DB 中对应字段为 `null`：显示「—」，**不要**再 fallback 到 0 或 110。

数字格式：与详情页 `formatScore` 一致（建议 1 位小数或整数，与现详情保持一致即可）。

## 4. 后端改造要点

### 4.1 列表 API（`src/server/kpi/kpi-query.ts`）

1. 扩展 `KpiPageData.rows` 类型：移除或废弃对外使用的单一 `score: string`；新增例如：
   - `selfScoreDisplay: string`
   - `leaderScoreDisplay: string`
   - `managerScoreDisplay: string`
   - `finalScoreDisplay: string`  
   或 `scores: { self: string; leader: string; manager: string; final: string }`（值为 `"—"` 或格式化数字字符串）。

2. 新增小函数（建议单独文件如 `kpi-list-score-display.ts` 便于单测）：
   - `formatKpiListStageScore(value: number | null | undefined, stageCompleted: boolean): string`

3. 列表行组装处**删除** `finalScore ?? managerScore ?? …` 兜底链用于展示。

4. **完成度 `progress`**（可选，建议二期）：当前按指标项 `final ?? manager ?? leader ?? self ?? 0` 会虚高；本交接不强制改，若开发顺手可改为「仅统计已完成阶段」或按阶段数比例，需产品确认。

### 4.2 写入逻辑（`src/server/kpi/actions.ts`，建议与列表同期在开发环境完成）

评分保存/提交时：

- **仅更新当前阶段对应的汇总字段**（及本阶段需要的项级 `selfScore`/`leaderScore`/`managerScore`）。
- **未进入的阶段**：`leaderScore` / `managerScore` / `finalScore` 保持 **`null`**，禁止用「满分 − 0 扣分」预写 110。
- 终审提交时再写 `finalScore`（现有：`managerTotal + attendanceScore`）。

避免开发修完列表后，新保存的数据仍被 actions 写脏。

### 4.3 与详情页计算对齐

详情汇总逻辑参考：

- `kpi-query.ts`（详情）：`selfTotal = scoreTotal - selfPenaltyTotal` 等。
- `actions.ts`：`calculatePenaltyTotal` + `scoreTotal - penalty`。

列表四列应直接读 **`PersonalKpi` 上已持久化的汇总字段**，且**严格按阶段完成标记**决定是否展示；不在列表侧重算项级分数（除非后续发现汇总字段不可靠再统一抽 `computeKpiStageTotals` 公共函数）。

## 6. 测试计划（开发环境）

### 6.1 单元测试（建议新增）

- `formatKpiListStageScore`：未完成 →「—」；完成 + 有值 → 格式正确；完成 + null →「—」。
- 列表行 mock：`selfReview` 完成、`leader` 未完成 → 仅「自评」有数，其余三列「—」。
- 审批链 KPI vs 无审批链 legacy 状态各一条。

### 6.2 手工验收（开发库 / 本地 `db/dev.db`）

| 场景 | 期望 |
|------|------|
| 初始化 / 自评中未提交 | 四列均为 — |
| 自评已提交，扣分后 &lt; 110 | 「自评」为实际分；后三列 — |
| 组长评进行中 | 自评有数；组长评/主管评/最终 —（除非组长阶段已完成） |
| 终审完成 | 四列均有数；「最终绩效总分」= 详情页一致；KPI 等级有值 |
| 列表不再出现「仅自评完成却整行 110」 | 通过 |

### 6.3 回归

- KPI 详情页评分、提交、退回流程不受影响。
- 权限与「查看 / 自评 / 组长评」操作链接不变。

## 7. 历史数据（开发 / 上现网前可选）

现网可能存在 **`leaderScore`/`managerScore` 被写成 110** 但审批步骤未完成的记录。

- **列表按阶段完成 + 对应字段展示**后，用户可见误展示会消失。
