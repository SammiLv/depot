# KPI 审批策略生产数据迁移方案

> 修订日期：2026-07-28
> 适用范围：SQLite 生产库升级到 KPI 审批策略配置化版本
> 核心原则：保留组织与用户、非 KPI 权限和年度指标管理数据；KPI 权限及 KPI 业务数据允许清理后重新配置

## 1. 数据边界

### 1.1 必须原样保留

#### 组织与用户

- `User`
- `OrgNode`
- `OrgClosure`

迁移前后必须保持：

- 行数不减少；
- 主键不变化；
- 用户与组织节点关系不变化；
- 用户角色、启停状态、登录信息不变化；
- 组织父子关系和闭包深度不变化。

#### 非 KPI 权限

- `MenuPermission`
- `RoleMenuPermission`
- `AnnualGoalPermission`
- `RoleAnnualGoalPermission`
- `OrgPermissionGrant` 中 `moduleKey <> 'KPI'` 的全部记录

说明：

- `OrgPermissionGrant` 是共享权限表，只允许重置 KPI 模块授权。
- `ANNUAL_GOAL` 及未来其他模块授权必须保留。
- 菜单权限属于共享访问控制，本轮不清理。

#### 年度指标管理数据

- `AnnualGoalPlan`
- `AnnualGoalMetric`
- `AnnualGoalMetricSource`
- `AnnualGoalQuarterTarget`
- `AnnualGoalProgress`
- `AnnualGoalRevisionLog`

这些数据是项目中的“指标管理”数据，与 KPI 评分模块分开，必须完整保留。

#### 其他非 KPI 业务数据

本轮不主动修改：

- `Project`
- `QuarterlyWork`
- `MonthlyWorkPlan`
- `WeeklyWorkUpdate`
- `RequirementValueTrack`
- `Notification`
- `TodoItem`
- 其他不属于 KPI 模块的业务表

### 1.2 允许清理并重新配置

#### KPI 权限

- `OrgPermissionGrant` 中 `moduleKey = 'KPI'` 的记录

清理后通过组织与权限页面重新配置 KPI 能力和作用范围。

#### KPI 模板及适用范围

- `KpiTemplateAssignment`
- `KpiTemplateItem`
- `KpiTemplate`

清理后重新导入或创建模板，并重新设置适用成员、组织节点或角色。

#### KPI 审批策略

- `KpiApprovalPolicyStep`
- `KpiApprovalPolicy`

清理后重新设置系统默认策略和部门覆盖策略。

#### 个人 KPI 和审批数据

- `PersonalKpiItemStepScore`
- `PersonalKpiActionLog`
- `PersonalKpiApprovalStep`
- `PersonalKpiItem`
- `PersonalKpi`

本次不迁移旧 KPI、旧评分和旧审批链，升级后按季度重新初始化。

## 2. 迁移目标

1. 保留库直接升级，不创建空库替换生产库。
2. 在同一生产数据库中清理允许重置的 KPI 数据。
3. 安全升级共享权限表 `OrgPermissionGrant`。
4. 补齐 KPI 新表、新字段和索引。
5. 对齐 Prisma migration history。
6. 重新配置 KPI 权限、模板和审批策略。
7. 重新初始化季度 KPI。
8. 验证必须保留的数据迁移前后完全一致。

## 3. 关键风险

### 3.1 禁止使用 db push

当前 `scripts/refresh-env-after-merge.sh` 包含：

```bash
npx prisma db push --config db/prisma.config.ts --accept-data-loss
```

生产环境禁止运行该命令。正式发布必须使用专门的生产迁移工具和 `prisma migrate deploy`。

### 3.2 共享权限表不能整表清空

`OrgPermissionGrant` 同时承载 KPI 和其他模块权限：

```text
moduleKey = KPI
moduleKey = ANNUAL_GOAL
```

只允许删除 KPI 行，不能执行：

```sql
DELETE FROM OrgPermissionGrant;
```

正确范围是：

```sql
DELETE FROM OrgPermissionGrant
WHERE moduleKey = 'KPI';
```

### 3.3 OrgPermissionGrant 结构升级

如果生产库仍是旧结构，需要新增：

- `subjectType`
- `userId`

迁移规则：

- 旧记录全部转换为 `subjectType='ROLE'`；
- `roleType` 原样保留；
- `userId=NULL`；
- 非 KPI 授权的 ID、模块、能力、范围、组织节点和启停状态必须原样保留。

如果生产库已经是新结构，则不重建、不改写非 KPI 授权。

### 3.4 KPI 表之间存在清理顺序

Prisma schema 中部分关联没有数据库外键约束，不能依赖级联删除。必须按子表到父表顺序显式清理，避免孤儿数据。

## 4. 生产库状态分型

预检工具必须把生产库归入以下状态：

| 状态 | 特征 | 处理方式 |
| --- | --- | --- |
| A：标准旧库 | migration history 连续，KPI 新结构未建立 | 数据备份后执行保全迁移和 `migrate deploy` |
| B：已 db push | KPI 新结构已存在但 migration 未登记 | 清理 KPI 数据，验证结构后对齐 migration history |
| C：混合状态 | 部分表或字段存在 | 运行幂等修复程序，验证后逐条对齐 history |
| D：异常库 | 完整性失败、存在失败 migration、保留数据异常 | 停止发布并专项修复 |

不能根据文件名或环境名称判断，必须检查：

- `_prisma_migrations`
- `sqlite_master`
- `PRAGMA table_info`
- 实际表数据

## 5. 生产迁移工具

### 5.1 只读预检工具

建议新增：

```text
scripts/preflight-kpi-production.ts
```

当前已实现，可通过以下命令运行：

```bash
npm run kpi:migration:preflight -- \
  --database /absolute/path/prod.db \
  --output /absolute/path/preflight.json
```

要求：

- 必须显式传入数据库绝对路径；
- 默认只读；
- 禁止回退到 `db/dev.db`；
- 输出 JSON 和控制台摘要；
- 任何阻断项返回非 0。

检查内容：

- SQLite `integrity_check`、`foreign_key_check`；
- migration 成功、失败和缺失记录；
- 相关表、字段和索引；
- 必须保留表的行数和内容摘要；
- `OrgPermissionGrant` 按 `moduleKey/subjectType` 统计；
- KPI 可清理表的行数；
- 数据库状态 A/B/C/D。

### 5.2 KPI 清理与结构修复工具

建议新增：

```text
scripts/migrate-kpi-production.ts
```

当前已实现。默认只做 dry-run：

```bash
npm run kpi:migration:run -- \
  --database /absolute/path/prod.db
```

正式执行必须同时提供备份、基线、结果文件和固定确认词：

```bash
npm run kpi:migration:run -- \
  --database /absolute/path/prod.db \
  --backup /absolute/path/backups/prod-before-kpi.db \
  --baseline-out /absolute/path/backups/prod-before-kpi.baseline.json \
  --result-out /absolute/path/backups/prod-kpi-migration-result.json \
  --execute \
  --confirm RESET_KPI_DATA
```

要求：

- 必须显式传入数据库绝对路径；
- 默认 dry-run；
- 真正执行时必须带明确参数；
- 使用 `BEGIN IMMEDIATE`；
- 任一步失败全部回滚；
- 不自动修改 `_prisma_migrations`。

职责：

1. 记录迁移前基线。
2. 安全升级 `OrgPermissionGrant`。
3. 只删除 KPI 权限。
4. 按依赖顺序清理 KPI 业务数据。
5. 补齐缺失的新表、新字段和索引。
6. 再次校验保留数据。
7. 输出执行报告。

### 5.3 迁移后验证工具

建议新增：

```text
scripts/verify-kpi-production.ts
```

当前已实现，可通过以下命令运行：

```bash
npm run kpi:migration:verify -- \
  --database /absolute/path/prod.db \
  --baseline /absolute/path/backups/prod-before-kpi.baseline.json \
  --output /absolute/path/backups/prod-kpi-verify.json
```

验证：

- 必须保留的数据行数和摘要与迁移前一致；
- KPI 权限和 KPI 业务表已经清空；
- 新结构完整；
- 无孤儿数据；
- migration history 对齐；
- 数据库完整性通过。

## 6. 迁移执行顺序

### 6.1 停止写入

1. 发布维护通知。
2. 停止 PM2/Node 服务。
3. 确认没有进程访问 SQLite。
4. 执行 WAL checkpoint。

SQLite 迁移期间不接受在线写入，本轮采用短时停机迁移。

当前生产服务约定：

```text
访问地址：http://depot.rj-info.com:80
监听地址：0.0.0.0:80
启动脚本：npm run start:office
```

生产 PM2 进程必须配置为运行上述启动脚本。迁移完成后的冒烟测试直接检查该生产地址。

### 6.2 创建可恢复备份

备份必须包括：

- 完整数据库文件；
- 当前应用版本或 Git commit；
- 当前 migration 列表；
- 预检报告；
- 数据基线报告；
- 备份 SHA-256。

备份完成后必须验证：

- 文件能够打开；
- `PRAGMA integrity_check` 返回 `ok`；
- 关键表可查询；
- 文件大小合理。

### 6.3 记录必须保留数据的基线

至少记录以下内容：

| 数据 | 校验方式 |
| --- | --- |
| `User` | 行数、ID 集合摘要、用户与组织关系摘要 |
| `OrgNode` | 行数、ID 和父子关系摘要 |
| `OrgClosure` | 行数、祖先/后代/深度摘要 |
| 菜单权限 | 各表行数和内容摘要 |
| 年度指标权限 | 各表行数和内容摘要 |
| 非 KPI 通用授权 | 行数和逐模块摘要 |
| 年度指标数据 | 六张表行数和内容摘要 |
| 其他非 KPI 业务表 | 行数摘要 |

内容摘要建议使用稳定排序后的 SHA-256，而不只比较行数。

### 6.4 清理 KPI 权限

结构升级完成后，仅执行：

```sql
DELETE FROM OrgPermissionGrant
WHERE moduleKey = 'KPI';
```

删除前后必须确认：

- `moduleKey <> 'KPI'` 的行数一致；
- 非 KPI 授权摘要一致；
- 没有误删 `ANNUAL_GOAL` 授权。

### 6.5 清理 KPI 业务数据

按以下顺序：

```text
1. PersonalKpiItemStepScore
2. PersonalKpiActionLog
3. PersonalKpiApprovalStep
4. PersonalKpiItem
5. PersonalKpi
6. KpiApprovalPolicyStep
7. KpiApprovalPolicy
8. KpiTemplateAssignment
9. KpiTemplateItem
10. KpiTemplate
```

全部清理后逐表确认行数为 0。

不得清理：

- `AnnualGoal*`
- `Project/QuarterlyWork*`
- 用户、组织和共享权限表中的非 KPI 数据

### 6.6 补齐 KPI 新结构

需要确保：

- `KpiApprovalPolicy`
- `KpiApprovalPolicyStep`
- `PersonalKpiItemStepScore`
- `PersonalKpi` 的审批策略快照字段
- `PersonalKpiApprovalStep` 的步骤快照和动作字段
- 全部目标索引

因为个人 KPI 已允许清空，所以不需要迁移或回填旧审批快照数据。

## 7. OrgPermissionGrant 数据保全升级

### 7.1 旧结构

使用新表复制方式：

1. 创建 `_migrate_OrgPermissionGrant_new`。
2. 复制所有旧授权，增加：
   - `subjectType='ROLE'`
   - `userId=NULL`
3. 校验：
   - 总行数一致；
   - ID 集合一致；
   - 非 KPI 授权内容摘要一致；
   - `roleType` 无丢失。
4. 校验通过后替换旧表并创建新索引。
5. 删除 `moduleKey='KPI'` 的授权。

### 7.2 新结构

如果 `subjectType/userId` 已存在：

1. 不重建共享权限表。
2. 记录所有非 KPI 授权摘要。
3. 删除 KPI 授权。
4. 验证非 KPI 授权摘要完全一致。

### 7.3 事务要求

共享权限表升级、KPI 权限删除和 KPI 业务清理应在同一 `BEGIN IMMEDIATE` 事务内完成。任何保留数据摘要变化都必须触发回滚。

## 8. Migration history 对齐

相关 migration：

1. `20260717160000_add_org_permission_grant`
2. `20260717170000_org_permission_subject_type`
3. `20260720000100_add_kpi_approval_policy`
4. `20260720000200_add_kpi_approval_policy_step`
5. `20260727000100_extend_personal_kpi_approval_snapshot`
6. `20260727000200_add_personal_kpi_item_step_score`

规则：

- migration 尚未执行且目标结构不存在：由 `migrate deploy` 执行。
- 结构已由 `db push` 或修复工具完成：逐项验证后才能执行：

```bash
npx prisma migrate resolve --applied <migration-name> --config db/prisma.config.ts
```

当前已提供带结构、清理结果和保留数据基线校验的对齐工具。先执行 dry-run：

```bash
npm run kpi:migration:align -- \
  --database /absolute/path/prod.db \
  --baseline /absolute/path/backups/prod-before-kpi.baseline.json
```

确认输出后正式对齐：

```bash
npm run kpi:migration:align -- \
  --database /absolute/path/prod.db \
  --baseline /absolute/path/backups/prod-before-kpi.baseline.json \
  --execute \
  --confirm ALIGN_KPI_MIGRATION_HISTORY
```

- 不允许为了消除错误直接批量标记 applied。
- 不允许修改已经在生产登记过的 migration。

对齐后执行：

```bash
npx prisma migrate deploy --config db/prisma.config.ts
npx prisma migrate status --config db/prisma.config.ts
```

最终必须显示数据库已是最新状态。

## 9. 迁移后重新配置

迁移结构成功后，按以下顺序恢复 KPI 业务：

1. 配置 KPI 角色权限和指定用户权限。
2. 创建并启用系统默认审批策略。
3. 按需要创建部门覆盖策略。
4. 导入或创建 KPI 模板。
5. 设置模板适用范围。
6. 验证策略能解析出审批人。
7. 初始化目标季度 KPI。
8. 抽查成员、组长、主管、管理员的查看和操作权限。

在系统默认审批策略、KPI 权限和模板未配置完成前，不执行季度 KPI 初始化。

## 10. 迁移后校验

### 10.1 必须保留数据

迁移前后必须满足：

- 组织、用户行数和摘要一致；
- 非 KPI 权限行数和摘要一致；
- 年度指标六张表行数和摘要一致；
- 其他非 KPI 业务表行数不减少。

### 10.2 允许重置数据

重新配置前必须满足：

- KPI 权限数量为 0；
- KPI 模板相关表数量为 0；
- KPI 策略相关表数量为 0；
- 个人 KPI 相关表数量为 0。

重新配置后必须满足：

- 恰好一个启用中的系统默认审批策略；
- 同一部门最多一个启用策略；
- 每个启用策略至少生成一个有效审批步骤；
- KPI 权限符合管理员确认的权限矩阵；
- 模板和适用范围符合业务配置；
- 新 KPI 能生成完整策略快照。

### 10.3 数据库检查

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

必须满足：

- `integrity_check` 返回 `ok`；
- `foreign_key_check` 无结果；
- `prisma migrate status` 显示 up to date。

## 11. 回滚方案

### 11.1 回滚触发条件

出现以下任一情况立即回滚：

- 组织或用户数据变化；
- 非 KPI 权限摘要变化；
- 年度指标数据摘要变化；
- 数据库完整性失败；
- migration 出现 failed 状态；
- 新版应用无法启动；
- KPI 重新配置或初始化无法完成。

### 11.2 回滚步骤

1. 停止新版服务。
2. 保留失败后的数据库和日志作为证据。
3. 恢复升级前数据库备份。
4. 恢复上一版应用代码和依赖。
5. 启动旧版服务。
6. 验证登录、组织、权限和年度指标。
7. 验证旧 KPI 页面能够按旧版本正常访问。

数据库和应用必须一起回滚。
