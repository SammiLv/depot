## 2. 改造背景

当前审批节点方案使用以下技术选项：

```text
跟随员工当前团队
跟随员工所属部门
固定组织节点
不使用组织节点
```

该方案仍存在以下问题：

1. “团队”和“部门”来自数据库节点类型，不符合管理员配置审批流时的业务语言。
2. 不同部门的组织深度可能不同，固定层级和 `ancestorDepth` 无法自然适配。
3. 系统无法判断在四级、五级组织中只审批两级时应该跳过哪个管理层。
4. 一个部门可能存在多套审批规则，现有“部门只启用一条策略”无法表达子组织差异。
5. 如果使用人工优先级数字解决多策略冲突，管理员难以判断最终实际使用哪条审批流。
6. 系统级策略需要覆盖大量部门、组和中间组织节点，平铺复选框要求管理员逐项勾选，真实组织规模下配置和复核成本过高。
7. 单纯把平铺列表替换为组织树只能改善查找，若缺少按层展开、按层全选和常用节点集合快捷选择，仍不能解决中间组织层级的批量配置问题。
8. 当前方案还需要为后续会签、或签、角色审批和条件审批保留稳定扩展边界，避免届时推翻本轮的组织作用域和审批快照设计。

最终方案不再由系统猜测“直属、上级、部门”关系，而是拆分为两个明确概念：

```text
审批流作用域：决定一名员工使用哪条审批流
审批方式：决定选中的审批流如何生成审批人
组织节点选择器：决定“组织节点负责人”步骤批量配置哪些实际组织节点
```

## 3. 最终产品模型

## 3.1 审批流作用域

每条审批流必须配置适用组织范围。

支持两类作用域：

1. 系统默认：未匹配任何组织策略时使用。
2. 指定组织节点及其全部下级：可选择部门、组或更深层组织节点，可多选。

示例：

```text
审批流1：适用于产品部及其下级
审批流2：适用于采购组及其下级
```

采购组员工同时落入两个范围时，使用范围更具体的审批流2；平台组员工只匹配审批流1。

## 3.2 审批流选择规则

一份 KPI 最终只能选择一条审批流，不叠加执行多条审批流。

选择顺序固定为：

```text
距离员工最近的组织作用域
→ 上级组织作用域
→ 系统默认策略
→ 兼容审批链
```

具体规则：

1. 最深、最具体的组织作用域优先。
2. 同一个组织节点不能绑定两条启用审批流。
3. 父级和子级作用域可以分别绑定不同策略，子级自动覆盖父级。
4. 不同组织分支可以分别绑定不同策略，互不冲突。
5. 同一条策略可以绑定多个互不冲突的组织节点，以复用相同审批规则。
6. 不增加人工填写的策略优先级数字。
7. 如果业务要求连续执行两种审批规则，应把它们配置在同一条审批流中，而不是启用两条相同作用域的审批流。

## 3.3 审批方式

审批节点下拉只保留两种方式：

```text
组织节点负责人
逐级审批至部门
```

### 组织节点负责人

管理员在一个审批步骤中明确选择参与该步骤的组织节点，可多选。

组织节点采用可展开、可收起的树形选择器。为适配系统管理员维护大规模组织，选择器支持按策略作用域根节点计算组织层级，并通过“展开下一层、收起一层、全选当前层、清空当前层”批量维护实际节点。批量操作的最终结果仍保存为明确的组织节点集合，管理员可以继续手动取消或补充特殊节点。

例如：

```text
第一级：直属组长审批
审批组织节点：采购1组、采购2组、B端1组、B端2组

第二级：上级组长审批
审批组织节点：采购组、平台组、B端组

第三级：部门主管审批
审批组织节点：产品部
```

系统针对当前员工，在其组织祖先路径中匹配每一步选择的节点：

- 匹配一个节点：使用该节点负责人。
- 没有匹配节点：该步骤对当前员工不适用，不生成审批快照步骤。
- 同一步匹配多个节点：配置存在歧义，保存时禁止。
- 匹配到节点但负责人缺失：按照“无人时允许跳过”处理。

同一步允许选择不同组织分支、不同深度的节点，但同一条根到叶路径中最多只能选择一个节点。

组织层级按所选策略作用域的组织根计算，而不是按页面当前偶然展开的节点计算。例如系统默认策略从公司组织根计算，第 1 层可对应各部门，第 2 层对应部门直属组织。不同分支深度不一致时，按层批量选择后允许人工增减节点，保存时仍执行祖先/后代冲突校验。

### 逐级审批至部门

从员工直属组织开始，沿员工祖先路径逐级生成所有有效组织负责人，直到所属部门主管截止。

固定规则：

1. 包含员工路径中的全部组织负责人。
2. 在部门节点结束，不进入公司级节点。
3. 不提供“最多几级”配置。
4. 不由系统自动删除任何中间管理层。
5. 自动适应新增、减少或调整后的组织层级。

如果需要公司级审批，可在同一条审批流中另外增加“组织节点负责人”步骤并选择公司节点；该步骤可以自动使用公司节点负责人，也可以指定审批人。

## 3.4 审批人覆盖

“组织节点负责人”步骤保留“审批人（可选）”：

- 留空：根据审批组织节点自动解析负责人。
- 指定用户：指定用户覆盖该步骤自动匹配的负责人。

“逐级审批至部门”步骤的审批人固定为自动匹配，不允许指定用户覆盖。该模式会沿员工组织路径生成多个依次审批的负责人；如果需要插入某个指定用户，应另外增加一个“组织节点负责人”步骤。

以下现有控制项继续保留：

- 跳过本人
- 去重审批人
- 找不到负责人时允许跳过
- 找不到负责人时禁止跳过

当“组织节点负责人”和“逐级审批至部门”解析出同一审批人时，按照去重规则只保留第一次出现的审批步骤。

## 3.5 后续审批能力扩展边界

本轮不实现会签、或签、角色审批和条件审批，但内部设计必须避免假设“一个配置步骤永远只产生一个审批人”。长期模型统一为：

```text
审批策略
  └─ 审批阶段（按顺序执行）
       ├─ 进入条件
       ├─ 审批人解析规则
       └─ 通过规则
```

扩展语义：

1. 审批人解析规则负责返回零个、一个或多个候选审批人；本轮实现组织节点负责人和逐级审批至部门，后续可以增加指定角色、项目负责人、指标负责人等解析器。
2. 通过规则负责定义同一审批阶段的完成条件；后续支持单人审批、会签（全部通过）和或签（任一通过）。
3. 进入条件负责决定审批阶段是否执行；后续支持按组织、KPI 类型、评分、状态等稳定业务字段组合条件。
4. “逐级审批至部门”表示多个组织负责人依次审批，不等同于同一阶段内的会签或或签。
5. KPI 初始化时必须冻结命中的策略、条件判断结果、审批人集合、阶段关系和通过规则，组织、角色或条件配置变化不得影响进行中的审批。
6. 本轮不为尚未实现的功能创建无用途配置字段；通过解析器接口、阶段标识和快照边界保证未来可以使用新增 migration 增量扩展。

## 3.6 不适用步骤与缺失负责人

必须区分两种情况：

### 步骤不适用

当前员工的组织祖先路径没有命中该步骤配置的任何组织节点。该步骤不生成，不视为异常。

### 负责人缺失

当前员工命中了配置节点，但该节点没有有效负责人。此时根据“无人时允许跳过”决定跳过或阻止 KPI 初始化。

## 4. 配置界面设计

## 4.1 策略基础信息

```text
策略名称
说明
适用组织范围（可多选，自动包含下级）
保存后立即启用
```

系统默认策略不选择组织节点；组织策略至少选择一个组织节点。

## 4.2 审批步骤

每个步骤显示：

```text
审批步骤名称
审批方式
审批组织节点（组织节点负责人模式显示，可多选）
审批人（组织节点负责人模式可选；逐级模式固定自动匹配）
跳过本人
去重审批人
无人时允许跳过
```

选择“逐级审批至部门”时，不显示审批组织节点选择器，并将审批人控件显示为不可编辑的“自动匹配：逐级负责人，截止到部门”。

## 4.3 组织树与按层批量选择

“组织节点负责人”的节点选择区改为标准组织树：

1. 节点可以逐级展开和收起，默认只展开到便于理解策略范围的层级。
2. 提供节点搜索、展开全部、收起全部和清空已选；不提供会同时选中上下级节点的无条件“全选整棵树”。
3. 提供“展开下一层”和“收起一层”，一次展开或收起当前作用域下所有分支的相邻层。
4. 当前层级由策略作用域根稳定计算，不取决于页面当前哪些节点偶然展开；为保持工具栏简洁，不单独展示层级说明。
5. 提供“全选当前层”和“清空当前层”，用于批量配置中间组织层级。
6. 搜索、展开全部、收起全部、清空已选、展开下一层、收起一层、全选当前层和清空当前层在同一行显示；搜索框使用紧凑宽度，其他操作使用轻量文字按钮。
7. 批量选择后允许逐项取消或补选特殊节点。
8. 同一步批量操作产生祖先/后代冲突时，不静默保存；界面应自动取消冲突项或明确提示管理员处理，服务端继续执行最终校验。

典型配置：

```text
部门主管审批：展开第 1 层 → 全选当前层
二级组长审批：展开第 2 层 → 全选当前层 → 调整特殊节点
一级组长审批：展开第 3 层 → 全选当前层 → 调整特殊节点
```

本轮按层和快捷操作保存的是操作当时明确命中的组织节点 ID，不默认动态包含未来新增节点。若后续增加“自动包含未来新增下级”，必须作为单独、默认关闭的规则型配置，并在启用前明确提示可能改变新 KPI 的审批链。

## 4.4 节点选择校验

“组织节点负责人”模式保存前校验：

1. 至少选择一个组织节点。
2. 节点存在且有效。
3. 节点位于策略允许配置的组织范围内，或属于明确允许的公司级公共节点。
4. 同一步选择的节点不能在同一条祖先路径上形成祖先与后代关系。
5. 部门管理员只能选择其管理范围内的节点。

## 4.5 审批链预览

保存策略前允许选择一个示例员工，展示：

```text
最终匹配的审批流
匹配到的策略作用域
每一步匹配的组织节点
自动匹配或指定的审批人
不适用而被省略的步骤
负责人缺失的步骤
去重后的最终审批链
```

策略列表摘要需要展示：

- 策略适用的组织范围。
- 是否为系统默认策略。
- 两种审批方式及所选组织节点。
- 当前是否启用。
- 是否覆盖了父级策略。

## 5. 建议数据模型

具体字段名可在第一轮开发时结合现有 Prisma 模型最终确定，模型需要满足以下能力。

## 5.1 策略作用域

增加策略与组织节点的多对多作用域关系，例如：

```text
KpiApprovalPolicyScope
- id
- policyId
- orgNodeId
- createdAt
```

约束建议：

- 同一策略不能重复绑定同一组织节点。
- 同一组织节点不能同时绑定两条启用策略。
- 同一策略内部不建议同时绑定祖先和后代节点，避免冗余覆盖。

系统默认策略继续使用独立的系统范围标识，不创建虚拟组织节点。

## 5.2 审批步骤模式

审批步骤模式收敛为：

```text
ORG_NODE_OWNER
CASCADE_TO_DEPARTMENT
```

旧的以下模式不再作为新界面选项：

```text
CURRENT_TEAM
CURRENT_DEPARTMENT
FIXED_NODE
NONE
```

## 5.3 步骤组织节点

“组织节点负责人”步骤增加多选组织节点关系，例如：

```text
KpiApprovalPolicyStepOrgNode
- id
- policyStepId
- orgNodeId
- createdAt
```

同一步不能重复绑定同一组织节点。

## 5.4 审批快照

一个“逐级审批至部门”配置步骤可能展开为多个审批快照步骤。

审批快照应保存：

- 原策略 ID 和名称。
- 原配置步骤 ID 和顺序。
- 最终快照步骤顺序。
- 配置审批方式。
- 匹配到的组织节点。
- 最终解析角色。
- 指定审批人覆盖信息（仅组织节点负责人模式）。
- 最终审批人。
- 步骤展示名称。

组织架构、节点负责人或策略之后发生变化，不影响已生成的审批链。

## 5.5 兼容字段

- `ancestorDepth` 仅保留旧数据兼容读取，不再由新界面写入。
- 当前已实现的节点模式在过渡期保留读取能力。
- 生产环境允许清理旧 KPI、旧策略和旧审批链，因此不要求自动迁移旧策略配置。
- 当前测试数据库已登记上一版节点 migration，后续模型调整应新增 migration，不修改已应用 migration 的内容。

## 5.6 可扩展解析与阶段边界

本轮实现应在服务层统一审批人解析器输入输出，避免页面、Server Action 和 KPI 初始化分别实现业务判断：

```text
输入：策略、配置步骤、员工、组织路径、KPI 上下文
输出：零个、一个或多个有顺序的审批解析结果，以及省略或失败原因
```

当前“组织节点负责人”通常返回零个或一个结果；“逐级审批至部门”可以返回多个串行结果。未来角色解析器可以返回多人集合，会签和或签再通过阶段通过规则解释多人集合。本轮只建立清晰接口和快照边界，不提前创建未使用的会签、或签或条件配置表。

## 6. 审批流解析流程

KPI 初始化时按照以下顺序执行：

1. 获取员工当前组织节点及完整祖先路径。
2. 查找所有启用且作用域包含员工的组织策略。
3. 选择匹配节点距离员工最近的策略。
4. 没有组织策略时选择系统默认策略。
5. 没有配置策略时进入兼容审批链。
6. 按策略步骤顺序解析审批方式。
7. “组织节点负责人”在员工路径中匹配所选节点。
8. “逐级审批至部门”展开员工路径中直到部门的所有负责人节点。
9. 仅对“组织节点负责人”应用指定审批人覆盖；逐级模式发现覆盖配置时拒绝保存或解析。
10. 应用跳过本人和审批人去重。
11. 根据无人处理规则跳过或报错。
12. 将最终结果完整写入审批快照。

## 7. 策略冲突规则

## 7.1 允许的配置

父子组织分别配置不同审批流：

```text
产品部及其下级 → 产品部默认审批流
采购组及其下级 → 采购专项审批流
```

采购组策略覆盖产品部策略。

不同组织分支配置不同审批流：

```text
采购组及其下级 → 采购审批流
平台组及其下级 → 平台审批流
```

两个范围不会同时匹配同一员工。

## 7.2 禁止的配置

同一个组织节点不能绑定两条启用审批流：

```text
采购组及其下级 → 审批流1
采购组及其下级 → 审批流2
```

启用第二条时应明确提示冲突策略和冲突节点。

## 7.3 不叠加策略

员工同时命中父级和子级策略时，只使用子级策略，不把两条审批流拼接。

如果业务要求先执行组织节点负责人，再执行逐级审批至部门，应配置在同一条审批流中：

```text
步骤1：组织节点负责人
步骤2：逐级审批至部门
```

## 11. 主要风险与控制

### 11.1 作用域冲突

风险：同一组织节点被多条策略覆盖，无法确定使用哪条。

控制：同节点只允许一条启用策略；父子范围按最具体节点自动选择；不允许人工优先级数字。

### 11.2 步骤节点匹配歧义

风险：同一步同时选择祖先和后代节点，一名员工可能命中多个节点。

控制：保存时使用组织闭包表校验，同一路径最多选择一个节点。

### 11.3 逐级步骤数量变化

风险：组织调整后，新 KPI 的审批步骤数量发生变化。

控制：这是逐级模式的预期行为；已生成 KPI 使用审批快照，不随组织调整变化。

### 11.4 策略适用但步骤不适用

风险：某些组织分支没有匹配到一个配置步骤。

控制：明确标记为“不适用步骤”并省略；预览中展示省略原因，不与负责人缺失混淆。

### 11.5 当前未提交实现需要重构

风险：上一版节点模式已经完成部分代码、测试和 migration，直接叠加会留下多套概念。

控制：在当前分支集中重构；保留有价值的审批快照、生产迁移和测试框架；新界面不再暴露旧模式；最终统一审查未提交改动。

### 11.6 大规模组织树性能

风险：真实生产组织节点远多于测试数据，一次渲染全部节点会造成弹窗卡顿，批量勾选也可能触发大量重复计算。

控制：组织树默认按需展开；层级和祖先关系在服务端或一次性索引中预计算；批量选择使用集合运算并一次更新状态；必要时对可见节点虚拟化；增加大规模模拟数据测试。

### 11.7 不同分支组织深度不一致

风险：同一个“第 N 层”在不同组织分支中可能代表不同业务角色，管理员误以为结构层级天然等于管理级别。

控制：界面明确显示层级计算根、节点数量和最终节点路径；批量选择只是配置快捷方式，不替代管理员业务判断；允许选择后手动增减并在保存前预览示例员工审批链。

### 11.8 批量选择与未来组织变化

风险：管理员误认为本次全选会自动覆盖以后新增的组织节点。

控制：本轮保存明确节点集合，并在界面注明“新增组织不会自动加入”；未来如实现动态包含规则，使用独立开关、默认关闭并记录配置版本。

### 11.9 未来审批能力反向侵入

风险：会签、或签、角色和条件审批直接叠加到现有步骤字段，导致串行步骤、阶段内多人和条件分支语义混乱。

控制：坚持“审批阶段—审批人解析规则—通过规则—进入条件”边界；本轮只建立可扩展接口和快照语义，未来能力采用新增模型、migration、自动化测试和独立界面逐项启用。
