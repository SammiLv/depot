## 2. 改造背景

当前 KPI 审批步骤通过“审批人类型 + 祖先层级”配置审批人。“祖先层级”使用数字表达员工所属组织向上的层级：

- `0`：当前组织节点
- `1`：上一级组织节点
- `2`：上两级组织节点
- 留空：由系统自动向上查找

该设计存在以下问题：

1. 管理员需要理解组织闭包表和 `depth` 的技术含义，配置门槛较高。
2. 仅看数字无法直接确认最终会在哪个组织节点查找审批人。
3. 组织层级调整后，原数字可能指向不同类型的组织节点。
4. “管理员”等不使用祖先层级的审批人类型仍会显示该输入框，容易误导。
5. 策略配置结果不够直观，不便于上线前复核。

本次改造将审批步骤调整为面向业务的配置方式：

```text
审批步骤名称 | 审批节点 | 审批人（可选）
```

## 3. 已确认的产品规则

### 3.1 审批步骤名称

审批步骤名称由管理员填写，例如：

- 采购1组组长审批
- 采购组组长审批
- 产品部主管审批
- 管理员终审

步骤名称会进入审批快照，并可作为 KPI 当前审批状态的展示文字。

### 3.2 审批节点

审批节点支持动态节点和固定组织节点。

动态节点：

- 跟随员工当前团队
- 跟随员工所属部门

固定组织节点：

- 从组织树中直接选择公司、部门或团队节点
- 示例：`公司 → 产品部 → 采购组 → 采购1组`

系统级策略需要保留动态节点能力，避免策略绑定某个具体部门后无法跨部门复用。

部门级策略只能选择该部门及其下级组织节点，不能选择其他部门节点。

### 3.3 默认审批人

审批人未指定时，系统根据审批节点类型自动匹配管理角色：

| 审批节点类型 | 默认管理角色 |
| --- | --- |
| 团队 | 组长（`TEAM_LEADER`） |
| 部门 | 部门主管（`DEPARTMENT_MANAGER`） |
| 公司 | 管理员（`ADMIN`） |

示例：

```text
步骤名称：采购1组组长审批
审批节点：采购1组
审批人：自动匹配采购1组组长
```

### 3.4 指定审批人

审批人字段为可选：

- 留空：根据审批节点和默认管理角色自动解析。
- 选择具体用户：指定用户覆盖节点默认管理角色。
- 审批节点留空：必须选择具体审批人。
- 审批节点和审批人不能同时为空。

部门级策略的指定审批人默认限制在当前部门范围内；系统级策略可以从全部有效用户中选择。

### 3.5 审批链快照

KPI 初始化时解析最终审批节点和审批人，并保存审批快照。

审批开始后，即使发生以下变化，已生成的审批链也不自动改变：

- 组织节点改名或移动
- 用户调岗
- 组长或部门主管发生变化
- 审批策略被修改

新初始化的 KPI 使用最新组织架构和审批策略。

### 3.6 原有控制项

以下能力继续保留：

- 跳过本人
- 去重审批人
- 找不到审批人时允许跳过
- 找不到审批人时禁止跳过

“祖先层级”不再出现在新配置界面中。

## 4. 建议的数据模型

审批步骤新增以下业务字段：

### 4.1 审批节点模式

建议增加枚举 `KpiApprovalNodeMode`：

```text
CURRENT_TEAM
CURRENT_DEPARTMENT
FIXED_NODE
NONE
```

含义：

| 值 | 含义 |
| --- | --- |
| `CURRENT_TEAM` | 跟随被考核员工当前团队 |
| `CURRENT_DEPARTMENT` | 跟随被考核员工所属部门 |
| `FIXED_NODE` | 使用管理员选择的固定组织节点 |
| `NONE` | 不依赖组织节点，必须指定审批人 |

### 4.2 固定组织节点

建议增加：

```text
approvalOrgNodeId String?
```

规则：

- `FIXED_NODE` 模式下必填。
- 其他模式下必须为空。
- 保存时校验节点存在、未失效且位于策略允许范围。

### 4.3 审批角色和指定用户

保留审批角色信息，用于记录节点默认管理角色；保留 `resolverUserId`，用于指定用户覆盖。

建议继续持久化最终解析所使用的角色，避免仅依赖界面推导：

```text
resolverType
resolverUserId
```

新配置的 `resolverType` 根据节点类型自动生成：

- 团队 → `TEAM_LEADER`
- 部门 → `DEPARTMENT_MANAGER`
- 公司 → `ADMIN`
- 指定用户覆盖 → `EXPLICIT_USER`

### 4.4 兼容字段

`ancestorDepth` 暂时保留在数据库中，但执行以下处理：

- 新界面不再显示或写入。
- 新策略统一写入 `null`。
- 服务端优先按新节点字段解析。
- 如存在历史策略，可在过渡期保留旧解析分支。
- 在确认生产环境不再存在旧策略后，再单独评估是否删除该字段。

本次生产迁移允许清理旧 KPI 策略、旧 KPI 和旧审批链，因此不要求把旧策略转换为新节点策略。

## 5. 审批人解析优先级

每个审批步骤按以下顺序解析：

1. 如果指定了有效审批人，直接使用指定审批人。
2. 否则根据审批节点模式确定目标组织节点。
3. 根据目标组织节点类型确定默认管理角色。
4. 在目标节点查找有效的对应角色用户。
5. 应用“跳过本人”规则。
6. 应用“去重审批人”规则。
7. 找不到审批人时，根据“无人时允许跳过”决定跳过或报错。
8. 将最终节点、角色、审批人和策略信息写入审批快照。

节点模式解析规则：

| 节点模式 | 解析方式 |
| --- | --- |
| `CURRENT_TEAM` | 使用员工当前团队节点 |
| `CURRENT_DEPARTMENT` | 使用员工最近的部门节点 |
| `FIXED_NODE` | 使用策略中保存的固定节点 |
| `NONE` | 不解析节点，必须使用指定审批人 |

## 6. 界面设计

### 6.1 步骤编辑区

每个步骤展示：

```text
审批步骤名称 | 审批节点 | 审批人（可选）
```

审批节点下拉建议按以下结构展示：

```text
动态节点
  跟随员工当前团队
  跟随员工所属部门

固定组织节点
  公司
    产品部
      采购组
        采购1组
```

### 6.2 审批人下拉

未选择具体用户时，显示自动匹配提示：

```text
自动匹配：采购1组组长
```

下方列出可指定用户：

```text
自动匹配：采购1组组长
张三
李四
王五
```

选择具体用户后，应明确显示：

```text
指定审批人：张三
```

### 6.3 策略摘要

保存后的策略列表需要展示可直接复核的业务摘要，例如：

```text
第1步：采购1组组长审批
审批节点：采购1组
审批人：自动匹配采购1组组长
```

动态节点示例：

```text
第1步：直属组长审批
审批节点：跟随员工当前团队
审批人：自动匹配团队组长
```

满足以下条件后视为改造完成：

1. 新策略配置界面不再出现“祖先层级”。
2. 管理员可以从组织树直接选择固定审批节点。
3. 系统级策略可以选择跟随员工团队或部门。
4. 审批人留空时能够自动匹配节点管理角色。
5. 指定审批人能够覆盖默认角色。
6. 配置界面能够清晰展示最终匹配规则。

9. 所有单元、集成、迁移、部署和回滚测试通过。
10. 生产构建通过，测试环境业务流程验收通过。

## 9. 风险与控制

### 9.1 固定节点失效

风险：组织节点被删除、停用或移出策略范围。

控制：

- 保存策略时校验。
- 启用策略前再次校验。
- 初始化 KPI 时执行最终校验。
- 不允许静默匹配到其他节点。

### 9.2 节点缺少管理角色

风险：组织节点没有有效组长或部门主管。

控制：

- 配置界面显示负责人缺失提示。
- 提供指定审批人覆盖能力。
- 严格执行“无人时允许跳过”开关。

### 9.3 系统策略绑定固定节点

风险：系统策略绑定某部门固定节点后，被其他部门错误复用。

控制：

- 系统策略优先推荐动态节点。
- 固定节点配置时显示影响范围提示。
- 策略摘要明确展示固定组织路径。

### 9.4 旧策略兼容

风险：旧策略仍包含 `ancestorDepth`。

控制：

- 过渡期保留旧数据读取能力。
- 新界面不再生成旧配置。
- 生产迁移按既定方案清理旧 KPI 策略和审批链。

### 9.5 migration history

风险：目标数据库通过 `prisma db push` 更新过结构，但 migration history 不完整。

控制：

- 生产迁移前先执行只读 schema diff。
- 只有实际结构与目标 schema 一致时才允许对齐历史。
- 对齐前必须创建完整数据库备份。
- 对齐后必须执行 `migrate status` 和保留数据校验。
