# 通知场景修改不生效 — 预置配置覆盖用户保存

**日期**：2026-08-31  
**环境**：生产（只查、未改代码）  
**模块**：通知中心 → 通知场景配置  
**现象**：编辑「周进度未更新提醒」，把执行日期从周一改为周五并点保存，再打开仍是周一。界面上像「保存没反应 / 改了又打回」。

---

## 结论摘要

保存接口本身可以把周五写入库。随后只要有管理权限的人打开（或刷新）通知中心页，服务端就会跑 `ensurePresetNotificationScenarios()`，按**场景名称精确匹配**，用代码里写死的预置 `scheduleConfig` 覆盖当前记录。该场景预置是 `weekdays: [1]`（周一），所以再进编辑仍是周一。

| 项 | 说明 |
|----|------|
| 根因 | 每次进通知页都用预置覆盖同名场景的定时配置 |
| 不是 | 周五按钮坏了、保存按钮没绑提交、权限拦保存（管理账号能点编辑就能保存） |
| 影响范围 | 所有**名称与预置完全一致**且带 `scheduleConfig` 的定时场景，不限于这一条 |
| 代码改动 | **无**（本次只记录） |

---

## 复现路径

1. 以可管理通知场景的账号进入「通知中心」→ 场景配置。
2. 打开「周进度未更新提醒」：频率每周、09:00、执行日周一。
3. 改成周五，点「保存」。弹窗可能关闭（保存成功）。
4. 再打开同一条：执行日仍是周一。

实际顺序：

1. `saveNotificationScenario` 把 `weekdays: [5]` 写入 `NotificationScenario.scheduleConfig`。
2. `revalidatePath("/notifications")` 触发页面重拉。
3. `page.tsx` 在拉列表前先执行 `ensurePresetNotificationScenarios()`。
4. 按 `name = "周进度未更新提醒"` 命中已有行，`scheduleConfig` 被预置盖回 `weekdays: [1]`。
5. 再打开编辑，读到的是覆盖后的库值。

因此：**保存可以成功，立刻被回写**。库里几乎看不到「曾经是周五」的中间态。

## 代码依据

### 1. 每次进通知页都同步预置

`src/app/(authenticated)/notifications/page.tsx`（约 29–31 行）：

```ts
if (canManage) {
  await ensurePresetNotificationScenarios();
}
```

有「管理通知场景」权限才会跑。普通只读用户进页不会覆盖；管理账号一进页就会覆盖。

同一函数还会在系统 bootstrap、seed 里调用。bootstrap 是登录触发的一次性保障；**真正高频的是通知页每次 SSR**。

### 2. 同名已存在时不是跳过，而是覆盖

`src/server/notifications/preset-scenarios.ts` 的 `ensurePresetNotificationScenarios()`（约 490–526 行）：

- 按 `name` 查找。
- 不存在 → `create`。
- **已存在** → `update`：至少覆盖 `description`、`module`；若预置带 `scheduleConfig`，再合并覆盖定时配置：

```ts
updateData.scheduleConfig = {
  ...currentSchedule,
  ...preset.scheduleConfig,          // 预置在后，用户改的 weekdays / timeOfDay / frequency 被盖掉
  daysBefore: preset.scheduleConfig.daysBefore,
};
updateData.nextRunAt = computeNextRunAt(updateData.scheduleConfig);
```

旧交接文档曾写「同名已存在则跳过」，**与当前代码不符**。

### 3. 该场景预置写死周一

`annualGoalWeeklySchedule`（约 24–31 行）：

- `frequency: "weekly"`
- `timeOfDay: "09:00"`
- `weekdays: [1]`（周一）
- `scanType: "annual_goal_weekly_progress_pending"`
- `daysBefore: 1`

场景名精确为 **「周进度未更新提醒」**，与线上弹窗一致。

## 影响范围

凡预置里带 `scheduleConfig` 的定时场景，用户改执行日 / 时间 / 频率后，管理账号再进通知页都会被打回预置。当前代码里包括：

| 场景名称 | 预置执行日（摘要） |
|----------|-------------------|
| 季度 KPI 初始化提醒 | 每周一 09:00 |
| 每日提醒未完成自评 | 每天 09:00 |
| **周进度未更新提醒**（本次报障） | **每周一 09:00** |
| 季度目标未拆解提醒 | 每周一 09:00 |
| 季度任务延期提醒 | 每周一 09:00 |
| 季度任务即将延期提醒 | 每周一 09:00 |
| 项目延期提醒 | 每周一 09:00 |
| 项目即将延期提醒 | 每周一 09:00 |
| 价值跟踪待完成提醒 | 每周一 09:00 |

事件触发（`EVENT`）场景没有 `scheduleConfig`，不会被这项合并打回执行日，但仍会每次进页更新说明和所属模块。

匹配键是 **名称全等**。改名后的记录不再被覆盖；同时会再插入一条原名预置。

## 容易误判的点（不是这次根因）

1. **「未更新天数」标签下面输入框被弹窗页脚挡住**  
   该扫描类型会显示这项，`daysBefore` 预置为 1，校验一般能过。表现为底部字段看不全，**不会**单独把执行日打回周一。

2. **执行日是多选 toggle，不是单选**  
   只点「周五」会变成 `[1, 5]`（周一仍在），除非再点掉周一。即便用户正确只留周五，保存后仍会被预置打回 `[1]`。

3. **表单 action 无 try/catch**  
   保存失败时界面可能「没反应」、弹窗不关。这次更符合「弹窗关了 / 再开又是周一」，即保存成功后被覆盖。

## 生产核实（不改代码）

查表 `NotificationScenario`，`name = '周进度未更新提醒'` 的 `scheduleConfig`（JSON）：

- 长期会看到 `"weekdays":[1]`。
- 保存瞬间若能抓到 Server Action，应曾写入 `[5]`，紧接着同一次页面刷新又写回 `[1]`。
- 可同时看 `updatedAt`：每次有管理权限的人打开通知页，同名预置行都会被 update（即使界面上没改）。

---

## 临时绕过（仍不改代码）

1. 把「周进度未更新提醒」**改名**（名称不要与预置完全一致）。
2. 在改名记录上把执行日设为周五并保存。
3. 下次进通知页会再插入一条原名预置（周一、启用）。把**新插的那条停用**，只留改名后的那条。

注意：管理账号每次进通知页仍会刷新原名那条预置的说明/定时配置；改名后的那条不受影响。

## 修复方向（尚未实施）

建议后续改代码时二选一或组合：

1. **已存在同名场景则跳过**（与旧交接文档口径一致），只补缺失预置。

3. **不要在通知页每次 SSR 调用** `ensurePreset`；放到 bootstrap / 显式「同步预置」操作即可。
