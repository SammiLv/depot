# Depot 部署后 Server Action 自动同步方案

**文档日期**：2026-08-07  
**适用环境**：生产自托管（`depot-prod.sh pull` 部署，`http://depot.rj-info.com`）  
**问题背景**：部署 rebuild 后，用户未刷新浏览器时提交表单报错  
`Server Action "…" was not found on the server`

---

## 1. 问题说明

### 1.1 现象

用户在「产品管理 → 新增项目」等页面提交表单时，出现：

```
Server Action "405256bdd7913f3b92a852fead87a5aaf1f9ab912e" was not found on the server.
Read more: https://nextjs.org/docs/messages/failed-to-find-server-action
```

服务端日志对应：

```
Failed to find Server Action "405256..."
This request might be from an older or newer deployment.
```

**Ctrl+F5 强刷后恢复正常。**

### 1.2 根因

| 项 | 说明 |
|----|------|
| 机制 | Next.js Server Action 在每次 **production build** 后会生成**新的 Action ID**（安全设计，非 bug） |
| 触发条件 | 用户浏览器仍运行**部署前**加载的旧 JS，表单提交携带**旧 Action ID** |
| 服务端 | 已运行**新 build**，无法识别旧 ID，请求在进业务逻辑前被拒绝 |
| 与数据无关 | **不删库、不改数据**；纯前后端 build 版本不一致 |

### 1.3 为何不能依赖用户手动刷新

- 用户不知道发生了部署
- 用户不关心「系统更新」
- 报错信息对业务用户无指导意义

**必须在应用层自动处理版本不一致。**

---

## 2. 方案对比

| 方案 | 思路 | 能否单独解决问题 | 推荐 |
|------|------|------------------|------|
| **A. Build 版本检测 + 自动刷新** | 轮询/聚焦时比对 BUILD_ID，不一致则自动 reload | ✅ 主方案 | ⭐⭐⭐ |
| **B. 捕获 Server Action 报错 + 自动刷新** | 提交失败且命中特定错误时 reload 一次 | ✅ 兜底 | ⭐⭐⭐ |
| **C. HTML Cache-Control** | HTML 响应 no-cache，减少整页被缓存 | ⚠️ 仅辅助 | ⭐ |
| **D. Vercel Skew Protection** | 新旧 build 短期并存 | 自托管不适用 | ✗ |
| **E. NEXT_SERVER_ACTIONS_ENCRYPTION_KEY** | 多实例同 build 密钥一致 | 不解决浏览器旧 JS | ✗ |

**推荐组合：A + B（可选加 C）**

---

## 3. 推荐实现：方案 A + B

### 3.1 方案 A — Build 版本检测 + 自动刷新（主方案）

#### 原理

1. 页面首次加载时，记录当前部署版本（`BUILD_ID`）
2. 后台定期（建议 60 秒）请求轻量 API 获取服务器当前 `BUILD_ID`
3. 用户**切回浏览器标签页**（`visibilitychange` / `focus`）时再查一次
4. 若与本地记录不一致 → 显示简短提示（可选）→ **`window.location.reload()`**

#### 新增文件

**（1）`src/app/api/build-id/route.ts`**

```typescript
import { readFileSync } from "node:fs";
import path from "node:path";

export const dynamic = "force-dynamic";

export function GET() {
  const buildIdPath = path.join(process.cwd(), ".next", "BUILD_ID");
  const buildId = readFileSync(buildIdPath, "utf8").trim();
  return Response.json(
    { buildId },
    {
      headers: {
        "Cache-Control": "no-store",
      },
    },
  );
}
```

**（2）`src/components/deployment-sync.tsx`**

Client Component，职责：

- 挂载时 fetch `/api/build-id`，保存 `initialBuildId`
- 每 60s 轮询一次
- `document.visibilitychange` 变为 visible 时检查
- `window.focus` 时检查（可选）
- 发现 `buildId !== initialBuildId` → reload

伪代码逻辑：

```typescript
"use client";

const POLL_INTERVAL_MS = 60_000;
const RELOAD_FLAG = "depot:deployment-reload";

async function fetchBuildId(): Promise<string | null> {
  const res = await fetch("/api/build-id", { cache: "no-store" });
  if (!res.ok) return null;
  const data = (await res.json()) as { buildId?: string };
  return data.buildId ?? null;
}

export function DeploymentSync() {
  useEffect(() => {
    let initialBuildId: string | null = null;
    let reloading = false;

    async function check() {
      if (reloading) return;
      const current = await fetchBuildId();
      if (!current) return;
      if (initialBuildId === null) {
        initialBuildId = current;
        return;
      }
      if (current !== initialBuildId) {
        reloading = true;
        // 可选：toast「系统已更新，正在刷新…」
        window.location.reload();
      }
    }

    void check();
    const timer = window.setInterval(check, POLL_INTERVAL_MS);
    const onVisible = () => {
      if (document.visibilityState === "visible") void check();
    };
    document.addEventListener("visibilitychange", onVisible);
    window.addEventListener("focus", check);

    return () => {
      window.clearInterval(timer);
      document.removeEventListener("visibilitychange", onVisible);
      window.removeEventListener("focus", check);
    };
  }, []);

  return null;
}
```

**（3）挂载到根 layout**

在 `src/app/layout.tsx` 的 `<body>` 内加入：

```tsx
import { DeploymentSync } from "@/components/deployment-sync";

// ...
<body>
  <DeploymentSync />
  {children}
</body>
```

#### 用户体验

- 部署后，多数用户在 60 秒内或切回页面时**静默刷新**
- 无需理解报错、无需 Ctrl+F5

### 3.2 方案 B — Server Action 报错自动刷新（兜底）

#### 原理

极少数用户在「轮询间隔内刚好点击提交」时，仍可能命中旧 Action。  
捕获 Next.js 返回的特定错误文案，**自动刷新页面一次**。

#### 识别条件（满足其一即可）

错误 message 包含：

- `Failed to find Server Action`
- `failed-to-find-server-action`
- `Server Reference ID did not match`

#### 防死循环

```typescript
const RELOAD_ONCE_KEY = "depot:server-action-reload";

function shouldAutoReloadForServerActionError(error: unknown): boolean {
  const message = error instanceof Error ? error.message : String(error);
  return /Failed to find Server Action|failed-to-find-server-action|Server Reference ID did not match/i.test(message);
}

function reloadOnceForStaleClient() {
  if (sessionStorage.getItem(RELOAD_ONCE_KEY)) return;
  sessionStorage.setItem(RELOAD_ONCE_KEY, "1");
  window.location.reload();
}
```

#### 接入方式（二选一）

**方式 1 — 在现有 client 表单提交处统一包装**

例如 `quarterly-work/content.tsx` 中 `createProject`、`createQuarterlyWork` 等 `try/catch`：

```typescript
try {
  await createProject(formData);
} catch (error) {
  if (shouldAutoReloadForServerActionError(error)) {
    reloadOnceForStaleClient();
    return;
  }
  throw error;
}
```

**方式 2 — 抽公共 helper（推荐）**

```typescript
// src/lib/run-server-action.ts
export async function runServerAction<T>(action: () => Promise<T>): Promise<T> {
  try {
    return await action();
  } catch (error) {
    if (shouldAutoReloadForServerActionError(error)) {
      reloadOnceForStaleClient();
      return new Promise(() => {}); // 等待 reload，不再抛错
    }
    throw error;
  }
}
```

业务侧：

```typescript
await runServerAction(() => createProject(formData));
```

#### 与方案 A 的关系

| 场景 | 处理方式 |
|------|----------|
| 部署后用户 idle 在页面上 | A 在轮询/聚焦时提前刷新 |
| 用户恰好在部署瞬间点击提交 | B 捕获报错后刷新一次 |
| 刷新后 | `sessionStorage` 可清除 reload 标记（页面 load 时 `removeItem`） |

---

### 3.3 方案 C — HTML 缓存策略（可选辅助）

在 `next.config.ts` 增加 headers，对 HTML 文档禁用长期缓存：

```typescript
async headers() {
  return [
    {
      source: "/:path*",
      headers: [
        {
          key: "Cache-Control",
          value: "no-cache, must-revalidate",
        },
      ],
      // 注意：需排除 _next/static 等静态资源，避免影响 JS/CSS 长期缓存
      // 实际实现时建议只对 document 请求生效，或使用 middleware 精细控制
    },
  ];
}
```

**局限**：对已打开的长驻标签无效；**不能替代 A/B**。

## 5. 验证计划

### 5.1 本地/预发

1. 启动服务，打开 `/quarterly-work`，DevTools Network 确认 `/api/build-id` 返回固定 `buildId`
2. 执行 `npm run build` + 重启（模拟部署）
3. **不手动刷新页面**，等待 ≤60s 或切换标签页再切回 → 应自动 reload
4. 在步骤 2 后立即点击「新增项目 → 创建」→ 若 A 未及时触发，B 应自动 reload 一次，第二次提交成功

### 5.2 生产

1. 低峰执行 `bash scripts/depot-prod.sh pull`
2. 保持一名测试账号页面不刷新，观察是否自动 reload
3. 另一名测试账号在 deploy 瞬间提交表单，确认无「Server Action not found」暴露给用户

### 5.3 日志

部署后 `logs/server.log` 中 `Failed to find Server Action` 应**显著减少或为零**。

## 6. 运维建议（非必须）

- 尽量在低峰窗口执行 `depot-prod.sh pull`（停机约 1～2 分钟）
- 若有内部通知渠道，可发「系统维护 1 分钟」——**不能替代** A/B，仅降低撞上部署的概率
- 部署后 `.next.backup/` 为旧 build 备份，与 Server Action 问题无关，可按现有策略清理

# 附录：产品管理页季度筛选默认 Q4 问题

**文档日期**：2026-08-07  
**页面**：`/quarterly-work`（菜单「产品管理」）  
**问题背景**：系统日期为 2026-01-03（日历 Q1），进入页面无 URL 参数时，筛选器却默认 **2026 年 + Q4 季度**

---

## A.1 现象

| 项 | 实际值 |
|----|--------|
| 系统日期 | 2026/1/3（1 月 → 自然季度应为 **Q1**） |
| 访问 URL | `http://depot.rj-info.com/quarterly-work`（无 `?year=&quarter=`） |
| 页面显示 | 年份 **2026**，季度 **Q4** |

用户从侧边栏点击进入，未手动选过季度。

---

## A.2 根因

**默认年/季不是按「今天日期」算的，而是按数据库里「最新一条季度工作（QuarterlyWork）」的 year/quarter。**

### 调用链

1. **`page.tsx`** — URL 无参数时 `selectedYear`、`selectedQuarter` 均为 `undefined`：

```typescript
// src/app/(authenticated)/quarterly-work/page.tsx
const selectedYear = parseIntParam(params?.year);        // undefined
const selectedQuarter = ... parseIntParam(params?.quarter); // undefined
const data = await getQuarterlyWorkData(currentUser, { selectedYear, selectedQuarter });
```

2. **`quarterly-work-query.ts`** — 计算 fallback 与 active 值：

```typescript
// src/server/quarterly-work/quarterly-work-query.ts（约 451–465 行）

const now = new Date();
const fallbackYear = works[0]?.year ?? now.getFullYear();
const fallbackQuarter = works[0]?.quarter ?? Math.floor(now.getMonth() / 3) + 1;

const activeYear = availableYears.includes(options?.selectedYear ?? Number.NaN)
  ? options!.selectedYear!
  : fallbackYear;

const activeQuarter = allQuarterSelected
  ? "all"
  : availableQuarters.includes(selectedQuarter ?? Number.NaN)
    ? selectedQuarter!
    : (availableQuarters.includes(fallbackQuarter) ? fallbackQuarter : availableQuarters[0]);
```

3. **`works` 的排序** — `works[0]` 是「年降序 + 季降序」的第一条：

```typescript
prisma.quarterlyWork.findMany({
  orderBy: [{ year: "desc" }, { quarter: "desc" }, { createdAt: "desc" }],
});
```

### 逻辑归纳

| 变量 | 优先级 |
|------|--------|
| `fallbackYear` | ① `works[0].year` ② 否则 `now.getFullYear()` |
| `fallbackQuarter` | ① `works[0].quarter` ② 否则日历当前季 `Math.floor(month/3)+1` |
| URL 无 `quarter` | 使用 `fallbackQuarter` |
| URL 无 `year` | 使用 `fallbackYear` |

因此：只要权限范围内存在 **2026 Q4** 的季度工作，且排序后排在 `works[0]`，即使用户在 **1 月（Q1）** 进入页面，也会默认 **Q4**。

**只有库里完全没有 QuarterlyWork 时**，才会 fallback 到日历季度（1 月 → Q1）。

### 与 KPI 页不一致

KPI 页（`/kpi`）无 URL 参数时，默认使用**当前日历**年/季：

```typescript
// src/server/kpi/kpi-query.ts（约 905–910 行）
const selectedYear = parsePeriodValue(periodOptions.selectedYear) ?? currentYear;
const selectedQuarter = ... ? periodOptions.selectedQuarter : currentQuarter;
```

产品管理页与 KPI 页的默认策略**不一致**，容易造成用户困惑。

### 与部署/删数据无关

- 非 Server Action 问题
- 非 rebuild 导致
- 非数据被删
- 纯**查询默认值**逻辑问题

---

## A.3 如何验证（测试/生产只读）

在生产或测试库执行（SQLite）：

```sql
SELECT id, title, year, quarter, status, createdAt
FROM QuarterlyWork
ORDER BY year DESC, quarter DESC, createdAt DESC
LIMIT 5;
```

若第一条为 `year=2026, quarter=4`，即与页面默认 Q4 现象一致。

---

## A.4 推荐修复方向（在测试环境实施）

### 目标

无 URL 参数时，默认年/季与 **当前自然年/季** 一致（与 KPI 页行为对齐），而不是跟 `works[0]` 走。

### 建议改法

**文件**：`src/server/quarterly-work/quarterly-work-query.ts`

**修改前（问题代码）：**

```typescript
const fallbackYear = works[0]?.year ?? now.getFullYear();
const fallbackQuarter = works[0]?.quarter ?? Math.floor(now.getMonth() / 3) + 1;
```

**修改后（建议）：**

```typescript
const calendarYear = now.getFullYear();
const calendarQuarter = Math.floor(now.getMonth() / 3) + 1;
const fallbackYear = calendarYear;
const fallbackQuarter = calendarQuarter;
```

或保留「有 URL 参数用 URL、无参数用日历」的分支，**不要用 `works[0]` 作为默认来源**。

### 可选增强

1. **首次进入写 URL**：无参数时 server 侧 `redirect` 到 `?year=2026&quarter=1`，便于分享链接与刷新保持筛选状态。
2. **年份下拉**：若 `calendarYear` 不在 `availableYears` 中，仍应出现在下拉并可选（当前逻辑对 year 有部分处理，改完后需回归）。
3. **单测**：为 `getQuarterlyWorkData` 增加 case——库内有 Q4 数据、当前日期为 Q1 时，默认季仍为 Q1。

## A.5 验证计划（测试环境）

1. 确保 DB 中存在 2026 Q4 的 QuarterlyWork（模拟生产现状）
2. 将系统日期设为 1 月（或等到 1 月），访问 `/quarterly-work`（无 query）
3. **修复前**：默认 Q4  
4. **修复后**：默认 Q1（2026 年）
5. 手动选择 Q4、刷新页面：若未做 URL redirect，确认是否回到 Q1（按产品设计决定）
6. 对比 `/kpi` 默认季，两页应一致

| 问题 | 结论 |
|------|------|
| 是否删数据导致 | **否** |
| 是否部署导致 | **否** |
