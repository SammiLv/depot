# 平台审计日志与业务日志建设方案

## 一、总体原则

建设一个统一的“审计中心”，集中查询全平台日志，但不要求所有日志物理写入同一张表。

推荐采用：

- 现有业务日志继续作为各业务模块的日志来源；
- 新增统一审计事件模型，补齐当前没有日志覆盖的操作；
- 审计中心通过统一查询服务聚合现有日志与新增审计事件；
- 同一个操作只保存一份权威日志，禁止为了两个展示入口重复写两份；
- 业务页面与审计中心共用同一份日志数据和查询逻辑。

## 二、展示入口分层

### 1. 同时在业务模块和审计中心展示

这些日志与具体业务对象直接相关，业务人员需要在原功能中查看上下文，管理员也需要在审计中心集中查询。

#### 现有业务日志

- 产品目标、项目、任务、需求、价值跟踪操作日志；
- KPI 保存、提交、评分、审批、退回、等级调整日志；
- 人才规则、人才盘点、工作事故、人才历史记录日志；
- 通知发送和投递结果日志。

#### 需要补齐的业务日志

- 权限配置变更；
- 组织架构、负责人、成员归属变更；
- 通知场景、接收人、发送渠道、机器人配置变更；
- 各业务模块的导入、导出操作；
- 账号启用、停用、角色调整和密码重置。

对应业务入口建议：

- 权限、组织日志：在组织架构或权限管理页面增加“操作记录”；
- 通知配置日志：在通知配置页面增加“操作记录”；
- 导入导出日志：在对应模块增加“导入导出记录”或“操作记录”；
- KPI、项目、人才等已有日志入口继续保留，逐步统一展示样式。

### 2. 只在审计中心展示

这些属于平台安全或运维行为，不对应普通业务对象，无需分散到业务页面。

- 登录成功、登录失败、退出登录；
- 生产环境拉取代码、数据库迁移、构建、启动、重启、停止；
- 发布版本、Git commit、Next.js Build ID、健康检查和回滚结果；
- 直接数据库修复、数据回填、批量维护；
- 审计归档、校验和审计日志异常。

## 三、审计中心功能位置

建议在左侧管理导航增加“审计中心”，仅管理员和专门授权的审计人员可见。

审计中心分为以下视图：

1. 全部操作；
2. 业务操作；
3. 账号、登录与权限；
4. 发布部署；
5. 数据维护；
6. 通知投递。

支持以下查询条件：

- 时间范围；
- 操作人员；
- 部门和小组；
- 功能模块；
- 操作类型；
- 业务对象；
- 成功或失败；
- Git commit、Build ID 或发布批次；
- 请求 ID 或批量操作关联 ID。

## 四、日志记录内容

每条日志建议包含以下信息：

### 操作者

- 操作用户 ID；
- 操作时的姓名快照；
- 操作者类型：用户、系统任务、部署脚本、数据维护；
- 登录方式；
- IP 和 User-Agent（脱敏、截断并正确处理可信代理）。

### 操作

- 模块；
- 稳定的操作代码；
- 中文操作名称；
- 成功或失败；
- 操作时间；
- 操作原因或备注。

### 业务对象

- 对象类型；
- 对象 ID；
- 对象名称快照；
- 所属部门或组织节点。

### 数据变化

- 修改前数据；
- 修改后数据；
- 发生变化的字段清单；
- 批量操作的数量、成功数和失败数。

敏感大文本不应完整写入日志，可只记录字段发生变化、摘要或哈希。

### 追溯信息

- requestId；
- correlationId；
- eventKey；
- Git commit；
- Next.js Build ID；
- 发布批次 ID；
- 服务器标识。

## 五、哪些操作必须记录

### 账号与权限

- 登录成功、失败和退出；
- 账号启用、停用；
- 密码重置；
- 角色调整；
- 权限授权、撤销、范围变更；
- 组织负责人调整；
- 人员组织归属变更。

### 业务数据

- 新增；
- 有效修改；
- 删除、软删除、恢复；
- 保存评分；
- 提交；
- 审批；
- 退回；
- 作废；
- 确认；
- 发布或停用规则；
- KPI 初始化；
- 批量维护。

“有效修改”是指数据库实际发生变化。重复点击保存但数据未变化时，不应产生新的业务审计日志。

### 文件与批量数据

- 导入文件；
- 导出数据；
- 下载敏感数据；
- 批量更新；
- 数据回填。

只记录文件名、文件 SHA-256、业务条件、数据条数和执行结果，不保存文件正文。

### 发布与数据维护

- Git 拉取的提交范围；
- 数据库备份；
- Prisma migration；
- 依赖安装；
- 生产构建；
- 服务停止、启动和重启；
- 健康检查；
- 回滚；
- 直接数据库修复。

## 六、哪些操作不记录为审计日志

以下行为不进入业务审计日志：

- 普通页面访问；
- 菜单和标签页切换；
- 搜索；
- 筛选；
- 排序；
- 分页；
- 下拉框选择但未提交；
- Toast 展示；
- 自动刷新和轮询；
- 静态资源请求；
- 未产生数据变化的重复保存。

如未来需要统计访问量和功能使用频率，应单独建设产品分析或访问指标，不要混入审计日志。

## 七、现有日志的复用和去重

### OperationLog

继续作为产品目标、项目、任务、需求和价值跟踪的业务日志来源。

审计中心通过适配器读取，不重复写入统一审计表。

### PersonalKpiActionLog

继续记录 KPI 提交、评分、审批、退回。

补齐“评分保存且数据实际发生变化”的日志，并记录变更摘要。不要再为同一次 KPI 操作另写一条完全重复的通用日志。

### KpiRatingAdjustmentLog

继续作为 KPI 等级调整的唯一权威日志。

### TalentActionLog

继续作为人才发展相关业务操作的日志来源，逐步补齐 before/after。

### NotificationDeliveryLog

继续记录实际发送渠道、状态和失败原因。

它不替代通知配置日志。通知场景、接收人和渠道配置变化需要单独记录业务审计事件。

### 状态表和时间字段

审批步骤、updatedAt、通知数据和 Git 历史不是完整审计日志，只能作为日志关联数据，不能回答完整的“谁在现网做了什么”。

## 八、写入机制

### 成功业务操作

审计日志与业务数据必须在同一个数据库事务中写入：

- 业务修改成功，日志同时成功；
- 日志写入失败，整个业务事务回滚；
- 避免出现业务已修改但没有日志。

### 失败操作

业务事务回滚后，另行记录失败事件：

- 登录失败；
- 权限拒绝；
- 导入失败；
- 发布失败；
- 数据修复失败。

失败日志只记录错误代码和安全摘要，不记录密码、Token 或完整敏感输入。

### 批量操作

使用一条批次主日志记录总体结果；确有逐条追溯要求时，再写对象子日志。

主日志与子日志通过 correlationId 关联。

## 九、数据安全与保留

禁止写入：

- 密码；
- Cookie；
- Session；
- Access Token；
- 钉钉密钥；
- 机器人 Webhook；
- 完整请求头；
- 无必要的薪酬、评价正文和个人敏感信息。

建议保留周期：

- 在线数据库保留最近 12 个月；
- KPI、人才、权限、组织和数据修复日志归档保留 5 年；
- 登录失败和通知投递日志保留 180 天；
- 具体周期最终结合公司制度和个人信息合规要求确认。

日志原则上只允许新增，不允许修改和删除。需要纠正时，追加一条更正事件。

归档文件应包含批次清单和哈希，用于发现篡改。

## 十、当前技术架构下的实现建议

当前为 Next.js、Prisma、SQLite 和单机生产环境，建议先采用简单可靠的方案：

- 新增统一 `AuditEvent` 模型；
- 提供统一审计写入服务；
- 提供统一查询和现有日志适配层；
- 在生产部署脚本中写入发布记录；
- 为数据修复提供专门脚本，禁止无记录地直接修改数据库；
- 审计中心按权限分页查询。

当前阶段不建议直接引入 Kafka、ELK 等重型组件。

以后出现多实例、日志量明显增长或需要集中安全分析时，再增加：

- Transactional Outbox；
- OpenTelemetry；
- Loki、OpenSearch 或 SIEM；
- 自动告警和异常行为检测。

技术可观测日志与业务审计日志必须分开存储，通过 requestId、buildId 和 releaseId 关联。

## 十一、实施顺序

### 第一阶段：补齐高风险空白

- 新增统一审计模型和查询权限；
- 登录和账号日志；
- 权限和组织变更日志；
- 通知配置日志；
- 导入导出日志；
- 发布部署日志；
- 数据修复日志；
- 审计中心基础查询页面；
- 适配现有五类日志。

### 第二阶段：业务操作全覆盖

- 梳理全部 Server Actions；
- 补齐新增、修改、删除、保存、提交、审批、退回、作废；
- 统一 before/after 和字段差异；
- 统一对象详情页操作记录。

### 第三阶段：归档与防篡改

- 自动归档；
- 哈希校验；
- 容量监控；
- 写入失败告警；
- 异常行为检测；
- 必要时接入统一日志平台。

## 十二、验收标准

- 任一关键数据变化均能查到操作者、时间、前后值和原因；
- 任一操作能定位到当时运行的 Git commit 和 Build ID；
- 权限、组织、通知配置和导入导出日志同时可在业务模块与审计中心查看；
- 登录、发布部署和数据库修复只在审计中心查看；
- 同一业务操作在审计中心只显示一次；
- 事务失败不会留下成功日志；
- 日志中不出现密码、Token、Cookie、Webhook 等敏感信息；
- 审计日志查询不会拖慢正常业务页面。
