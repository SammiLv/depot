## 2. 已确认决策

1. **配置权限**：走能力授权 `MANAGE_NOTIFICATION_SCENARIO`。默认给 `ADMIN` / `DEPARTMENT_MANAGER` / `TEAM_LEADER`。未授权看不到「场景配置」Tab。
2. **场景数据作用域**：首期**全系统共享**一套场景，有权限即可编辑；不做部门/小组隔离。
   - 实现上默认授权使用 `scopeType=ALL`（三角色均是），避免 NODE/SUBTREE 缺 `orgNodeId` 导致校验失败。与早期方案草稿「主管 SUBTREE / 组长 NODE」略有差异，以本交接为准。
3. **首期事件**：只覆盖 KPI 全流程 + 两类定时扫描；年度指标/季度工作等后续扩 `event-registry`。
4. **定时任务**：内嵌 Next.js，配置存场景表；**不使用 crontab**。

## 3. 架构摘要

```text
业务动作（KPI 初始化/提交/审批…）
        │
        ▼
 emitNotificationEvent(event, payload)
        │
        ▼
 NotificationEngine
   ├─ 查启用场景（EVENT 按 triggerEvent；SCHEDULE 由调度器带 scenarioIds）
   ├─ 解析接收人（recipientConfig）
   ├─ 渲染模板（{{var}}）
   ├─ 写 Notification（系统内）
   ├─ 调钉钉 sendMessage（可开关）
   └─ 写 NotificationDeliveryLog（去重 + 审计）

定时场景：
 instrumentation.ts → startNotificationScheduler()
   → 每 60s 扫 nextRunAt<=now 的 SCHEDULE 场景
   → 条件更新 nextRunAt 防重
   → 扫描数据后 emit(…, { scenarioIds })
```

核心原则：

- **钉钉失败不回滚业务**；系统内通知仍写入
- **业务侧 emit 失败只打日志**，不打断 KPI 主流程
- EVENT 场景只响应业务 emit；SCHEDULE 场景只由调度器按 `scenarioIds` 投递，避免双发

## 4. 数据模型

迁移目录：

- `db/prisma/migrations/20260810000100_add_notification_scenario/migration.sql`

### 4.1 权限扩展

- `OrgPermissionModuleKey` += `NOTIFICATION`
- `OrgPermissionAbilityKey` += `MANAGE_NOTIFICATION_SCENARIO`

默认授权写在：

- `src/server/permissions/permission-constants.ts` → `notificationDefaultPermissionGrants`
- `src/server/bootstrap/system-bootstrap.ts` → `ensureNotificationScenarioPermissions()`

### 4.2 `NotificationScenario`

| 字段 | 说明 |
|------|------|
| name / description / isActive / sortOrder | 基础信息 |
| triggerType | `EVENT` \| `SCHEDULE` |
| triggerEvent | 事件码，如 `kpi.initialized`；SCHEDULE 场景也会写入对应 emit 事件码 |
| scheduleConfig | Json：`frequency/timeOfDay/weekdays/scanType/daysBefore/timezone` |
| nextRunAt | 调度用，防重复执行 |
| recipientConfig | Json：接收人规则 |
| channelConfig | Json：渠道 + 模板 + 钉钉类型 |
| conditionConfig | Json?：可选过滤 |
| createdById / updatedById | 审计 |

### 4.3 `NotificationDeliveryLog`

- `(scenarioId, eventKey, channel)` 唯一
- `status`: `SENT` / `FAILED` / `SKIPPED`
- 去重窗口由 `recipientConfig.dedupeWindowHours` 控制（UI 默认 24）

现有 `Notification` 表继续作为「我的通知」主数据；首期未加 `scenarioId` 字段，审计看 DeliveryLog。

## 6. 首期事件与 KPI 接线

| 事件码 | 触发点 |
|--------|--------|
| `kpi.initialized` | `initializeQuarterlyKpis` 创建成功后 |
| `kpi.self_review.pending` | 初始化后；驳回回到自评；定时扫描 |
| `kpi.scoring.submitted` | 自评 submit 成功 |
| `kpi.approval.pending` | 进入下一步且有当前审批人 |
| `kpi.approval.approved` | 审批通过 |
| `kpi.approval.rejected` | 驳回 |
| `kpi.completed` | 状态到 `COMPLETED` |
| `todo.due_soon` | 定时扫描 `todo_due`（当前业务较少写 TodoItem，可能无命中） |

代码：`src/server/kpi/actions.ts`（`persistPersonalKpiScoring` / `initializeQuarterlyKpis`）。

### 预置扫描类型

| scanType | 含义 |
|----------|------|
| `kpi_self_review_pending` | `DRAFT` / `PENDING_SELF_REVIEW` 的 KPI |
| `todo_due` | 未完成且 `dueDate` 在 N 天内的 `TodoItem` |

## 7. 预置场景（本地已存在）

1. KPI 初始化提醒自评（EVENT / `kpi.initialized`）
2. KPI 提交后通知审批人（EVENT / `kpi.approval.pending`）
3. KPI 审批驳回通知（EVENT / `kpi.approval.rejected`）
4. KPI 终评完成通知（EVENT / `kpi.completed`）
5. 每日 09:00 提醒未完成自评（SCHEDULE / `kpi_self_review_pending`）

保证方式：

- 全量 seed：`npm run seed`
- 增量：登录触发 `ensureInitialSystemBootstrap()`，会调用 `ensurePresetNotificationScenarios()`（若同名预置已存在则跳过）

## 12. 建议验证清单

1. 管理员打开 `/notifications`，可见「场景配置」，列表有 5 条预置。  
2. 点「测试」：当前用户「我的通知」出现一条；钉钉开关关闭时不应真实外发。
