# 指标管理（年度目标）权限收归方案

> 日期：2026-08-24
> 状态：**方案待确认，未实施**
> 分支：depot-KPI

## 一、背景与目标

指标管理（年度目标）是最后一套独立权限模型：`AnnualGoalPermission`（代码播种的 5 个能力定义）+ `RoleAnnualGoalPermission`（scopeType SYSTEM/DEPARTMENT × roleType × allowed 布尔），与 KPI/人才发展/产品管理/通知共用的 `OrgPermissionGrant`（模块 × 能力 × 作用域 × 主体）并存。

目标：把指标管理收归到 `OrgPermissionGrant` 模型，启用 schema 中已预留但从未使用的 `OrgPermissionModuleKey.ANNUAL_GOAL`，矩阵配置、运行时判定、bootstrap 默认授权全部与人才发展模块同构；旧表保留只读，运行时与矩阵 UI 不再读写。

## 二、现状盘点（旧模型怎么工作）

### 2.1 能力点（5 个，代码播种）

定义在 `src/server/organization/annual-goal-permissions.ts` 的 `annualGoalPermissionDefinitions`：

| code | 名称 | 依赖 |
|---|---|---|
| `annualGoal.viewDepartmentPlans` | 查看部门方案 | — |
| `annualGoal.editDepartmentPlans` | 编辑部门方案 | 前置：查看部门方案 |
| `annualGoal.viewTeamPlans` | 查看小组指标 | — |
| `annualGoal.editTeamPlans` | 编辑小组指标 | 前置：查看小组指标 |
| `annualGoal.updateProgress` | 更新季度进度 | — |

「编辑前置查看」由 `getAnnualGoalCapabilities` 在代码里强制（`canEditX = canViewX && has(editX)`）。

### 2.2 矩阵存储与生效规则

- `RoleAnnualGoalPermission` 行：`scopeType=SYSTEM`（`departmentOrgNodeId=""`）为系统模板；`scopeType=DEPARTMENT` 为某部门覆盖行。
- 某用户生效值 = 其最近部门祖先的 DEPARTMENT 行 ?? SYSTEM 行（`resolveAnnualGoalPermissionScope` + `getScopedAnnualGoalPermissionMatrix` 的 `scopedRow ?? systemRow`）。
- **旧模型支持部门级显式关闭**：DEPARTMENT 行 `allowed=false` 可盖掉 SYSTEM 的 `allowed=true`（dev 库目前无此类行，全部为 allowed=true）。

### 2.3 运行时链路

- 入口三处：`annual-goals-query.ts`（`getAnnualGoalsData`，416–419 行）、`annual-goals/actions.ts`（`getAnnualGoalActionContext`，44–47 行）、`dashboard/dashboard-query.ts`（47、121 行）。统一模式：`getAnnualGoalPermissionMapForUser` → `getAnnualGoalCapabilities` → `buildOrgScopeContext` → where 构建 / 逐 plan 判定。
- 数据范围**由 roleType 硬编码推导**，与授权行无关：
  - `buildOrgScopeContext`：ADMIN → 全量；其余角色 teamScopeIds=自身节点子树、deptScopeIds=最近部门祖先子树（仅当有部门方案能力时）。
  - `getAnnualGoalPlanWhere` / `getAnnualGoalTeamWhere`：ADMIN 全量，其余按部门祖先/自身子树过滤。
  - `annual-goals-query.ts` 另有 4 处 `roleType === "ADMIN"` 硬编码：439/442/451 行（组织树导航范围）与 934 行（`showDepartmentNavigation`）。

### 2.4 dev 库当前矩阵实况（作为默认授权基线）

| 查看部门方案 | ✅ | ✅ | ✅ | ✅ |
| 编辑部门方案 | ✅ | ✅ | — | — |

## 三、目标模型与映射设计

### 3.1 新能力点（`OrgPermissionAbilityKey` 新增 5 个枚举值，`moduleKey=ANNUAL_GOAL`）

| 新能力点 | 对应旧 code |
|---|---|
| `VIEW_ANNUAL_GOAL_DEPARTMENT_PLANS` | annualGoal.viewDepartmentPlans |
| `EDIT_ANNUAL_GOAL_DEPARTMENT_PLANS` | annualGoal.editDepartmentPlans |
| `VIEW_ANNUAL_GOAL_TEAM_PLANS` | annualGoal.viewTeamPlans |
| `EDIT_ANNUAL_GOAL_TEAM_PLANS` | annualGoal.editTeamPlans |
| `UPDATE_ANNUAL_GOAL_PROGRESS` | annualGoal.updateProgress |

SQLite 该列为 TEXT 无约束，加枚举值只需 `prisma generate` + 重启，不需要迁移。

### 3.2 作用域映射（关键差异：不能照搬 KPI 的统一 role→scope）

KPI/人才发展用统一的角色→作用域映射（ADMIN=ALL、主管=SUBTREE、组长=NODE、组员=SELF），但指标管理的现状矩阵里**组员可查看部门方案、可更新进度**，统一映射的 SELF 会给不出组织节点范围。因此指标管理需要**按「能力 × 角色」各自的映射表**（`annualGoalPermissionScopeByAbilityRole`），矩阵保存/同步/读取共用同一份：

| 能力点 | ADMIN | 部门主管 | 组长 | 组员 |
|---|---|---|---|---|
| 查看部门方案 | ALL | SUBTREE@部门 | SUBTREE@部门 | SUBTREE@部门 |
| 编辑部门方案 | ALL | SUBTREE@部门 | — | — |
| 查看小组指标 | ALL | SUBTREE@部门 | NODE@本组 | — |
| 编辑小组指标 | ALL | SUBTREE@部门 | NODE@本组 | — |
| 更新季度进度 | ALL | SUBTREE@部门 | NODE@本组 | NODE@本组 |

说明：

- 「SUBTREE@部门 / NODE@本组」均按现有机制**物化为按部门的授权行**（`orgNodeId=部门节点`），解析时经闭包表匹配回用户实际范围；系统行（`orgNodeId=null`）只作矩阵模板，与 KPI/人才发展现状一致。
- 组长/组员的「查看部门方案」用 SUBTREE@部门：解析覆盖率 = 部门子树（含部门节点本身），与旧语义「最近部门祖先子树」等价。
- 组员的「更新季度进度」用 NODE@本组：解析时 NODE 授予节点（部门）是用户节点的祖先 → 覆盖集会收入用户自身所在组节点，与旧语义「本组」等价。

### 3.3 运行时改造设计

`annual-goal-permissions.ts` 保留对外的能力形状（`AnnualGoalCapabilities`、`AnnualGoalPlanPermissions`），内部改为 coverage 驱动，调用方改动最小：

1. `getAnnualGoalCapabilitiesForUser(user)`：改为并行 `resolvePermissionCoverage` 五个能力点；**保留编辑前置查看**（`canEditX = editCoverage.hasPermission && viewCoverage.hasPermission`）。
2. `OrgScopeContext` 改为四份节点集合：deptViewIds / deptEditIds / teamViewIds / teamEditIds（各取对应能力点 coverage 的 `orgNodeIds`，`hasAllAccess` 置空集合并以布尔直通）。比现在的「view/edit 共用一份 scope」更精确（授权可分别配置）。
3. `getAnnualGoalPlanPermissions`：逐 plan 判定改为「能力布尔 && ownerOrgNodeId ∈ 对应集合」，ADMIN 分支删除，改由 `hasAllAccess` 直通。
4. `getAnnualGoalPlanWhere` / `getAnnualGoalTeamWhere`：改为 `hasAllAccess → 不过滤；否则 ownerOrgNodeId/departmentOrgNodeId ∈ 集合并集`，无权限 → 既有的 `__no_annual_plan__` 哨兵。
5. `annual-goals-query.ts` 4 处 `roleType === "ADMIN"` 硬编码：439/442/451（组织树导航范围）与 934（`showDepartmentNavigation`）改为「查看部门方案 coverage 的 `hasAllAccess`」。

### 3.4 矩阵 UI 与同步机制

- 组织与权限页「指标管理权限」tab 从 `RoleAnnualGoalPermission` 切换到 `OrgPermissionGrant`，结构照搬人才发展 tab（草稿格、保存/重置、同步变更/全量同步、单格应用到所有部门）。
- `saveAnnualGoalRolePermissions`、`syncAnnualGoalPermissionMatrix`、`saveAndApplyAnnualGoalPermission{Changes,}ToAllDepartments`、`applyAnnualGoalPermissionToAllDepartments` 按 talent 版本改写，区别仅在 scopeType 取自 3.2 的「能力 × 角色」映射而非统一角色映射。
- 「部门级显式关闭」的表达能力：旧模型用 `allowed=false` 行，新模型用「删除该部门物化行」表达（SUBTREE/NODE 类角色效果等价）；ALL/SELF 类系统行全局生效、部门不可收回——与 KPI/人才发展已接受的行为一致。

### 3.5 行为变化点（需确认）

1. **组长/组员的小组范围从「本组子树」收窄为「本组单节点」**（与 KPI/人才发展的「组长=本组 NODE」对齐）。仅当小组节点下再挂子节点时才有差别；当前组织树无此形态，无实际影响。
2. **ADMIN 不再由代码硬编码放行**，改由 ALL 授权行生效（矩阵中 ADMIN 列成为可配置数据，与 KPI/人才发展一致；批量覆盖仍拒绝 ADMIN）。
3. 旧模型的部门级 `allowed=false` 显式关闭行无法逐行无损翻译（见 3.4）。dev 库无此类行；搬迁脚本会对目标库检测，若存在则列出并默认跳过（该部门回到系统模板值），由人工决策。
4. 查看/编辑的作用域集合分离后，若管理员把「编辑部门方案」配到比「查看部门方案」更窄的范围，编辑能力随编辑集合走（旧模型是共用一份 scope）。默认授权下两者相同，无感知变化。

## 四、实施清单（确认后按序执行）

1. **常量层**：`schema.prisma` 的 `OrgPermissionAbilityKey` 加 5 个枚举值（注释标注归属 ANNUAL_GOAL 模块），`AnnualGoalPermission`/`RoleAnnualGoalPermission` 模型加「已废弃，仅保留历史可读」注释；`permission-constants.ts` 新增 `annualGoalAbilityKeys`、`annualGoalMatrixPermissionAbilityKeys`、`annualGoalPermissionScopeByAbilityRole` 与默认授权矩阵（按 2.4 实况）。
2. **运行时**：`annual-goal-permissions.ts` 按 3.3 重写（删除矩阵段与播种函数）；`annual-goals-query.ts`、`annual-goals/actions.ts`、`dashboard-query.ts` 换入口并清理 4 处 roleType 硬编码。
3. **矩阵 UI**：`organization/actions.ts` 四个动作改写；`permission-matrix-sync.ts` 的 `syncAnnualGoalPermissionMatrix` 改写；`organization/page.tsx`/`content.tsx` 指标管理 tab 换 grant 数据源（沿用现有 tab 位置与交互）。
4. **bootstrap**：`system-bootstrap.ts` 新增 `ensureAnnualGoalPermissionGrants()`（幂等：系统行 + 按部门物化行，照搬 talent 模式），替换 `ensureAnnualGoalPermissions`/`ensureSystemAnnualGoalRolePermissions` 调用。
5. **数据搬迁脚本**：`scripts/annual-goal-permission-migration.ts`（幂等，可重复跑）：
   - 读 `RoleAnnualGoalPermission` 全部行，按 3.2 映射翻译为 `OrgPermissionGrant`（SYSTEM allowed=true → 系统行；DEPARTMENT allowed=true → 部门行；已存在则跳过）；
   - DEPARTMENT `allowed=false` 且系统为 true 的行：检测并打印清单，不翻译；
   - 输出翻译/跳过/冲突计数。
6. **测试**：`annual-goal-permissions.test.ts` 按新模型重写；`permission-matrix-sync.integration.test.ts` 更新指标管理用例。
7. **校验**：`tsc --noEmit --skipLibCheck`、eslint（不新增 error 类别）、单测全绿；用 ADMIN/主管/组长/组员四类账号走查指标管理页（部门方案列表、小组指标、进度更新按钮、组织树导航）与矩阵 tab（勾选保存、同步、单格覆盖）。
8. **交接文档**：本文件状态改为已实施，补执行结果。

## 五、上线数据操作（生产库，合并后执行一次）

1. 执行搬迁脚本：`npx tsx scripts/annual-goal-permission-migration.ts`，核对输出计数与 deny-override 清单（预期为空）。
2. 重启服务，`instrumentation.ts` 自动兜底默认授权（与脚本同一映射，双保险）。
3. 四类账号走查（同实施清单第 7 步），重点核对：组员可见本部门方案与进度更新入口、组长只见本组指标可编辑、主管部门级全覆盖。
4. 旧表 `AnnualGoalPermission`/`RoleAnnualGoalPermission` 保留只读，不删数据；确认稳定后再择机随「角色可配置」里程碑评估删表。

## 六、边界与注意

- 本方案只收归**权限模型**；指标管理业务逻辑（方案/指标/季度目标/进度）不动。
- KPI 审批策略（按金额/评分段配置审批人）不是权限，不在本次范围。
- `PermissionScopeType`（SYSTEM/DEPARTMENT）枚举仍被菜单权限（`RoleMenuPermission`）使用，保留。
- 合入 depot-clean/main 后即停手，迁移/generate/重启由 depot-clean 会话处理。
- 后续「角色可配置」里程碑中，`annualGoalPermissionScopeByAbilityRole` 这类按角色硬编码的映射需随之重构（角色变数据后，映射关系应入库），本方案先按现状落地。
